# 第一部分：数据流向（确切）

## 1. 全景图

```
┌──────────────┐        ┌──────────────────┐        ┌─────────────┐
│  客户端       │        │  我们的服务器      │        │  平台 CDN    │
│  小程序/App   │        │  FastAPI:8080    │        │  抖音/B站…   │
└──────┬───────┘        └────────┬─────────┘        └──────┬──────┘
       │                         │                          │
       │ ①解析 POST /api/parse   │                          │
       │────────────────────────►│                          │
       │                         │ ②抓页面（入网）           │
       │                         │─────────────────────────►│
       │                         │◄─────────────────────────│
       │ ③返回 JSON（出网 8KB）   │                          │
       │◄────────────────────────│                          │
       │                                                    │
       │ ④保存 wx.downloadFile（直连，不经过服务器）           │
       │──────────────────────────────────────────────────►│
       │◄──────────────────────────────────────────────────│
       │                                                    │
       │ ⑤封面 <image src="/api/proxy-cover?url=...">        │
       │────────────────────────►│ ⑥抓图（入网 100KB）      │
       │◄────────────────────────│─────────────────────────►│
       │  返回图（出网 100KB）     │◄─────────────────────────│
```

**一句话：视频 0 经过服务器；解析的 JSON 和封面图经过服务器。**

---

## 2. 逐条链路的真实数据量

### ① 解析 `POST /api/parse`

| 阶段 | 方向 | 数据量 | 说明 |
|---|---|---|---|
| 客户端上传请求 | 入网 | < 1 KB | 只有链接文本 + 参数 |
| 服务器抓平台页面 | **入网** | 150 KB（抖音）~ 800 KB（B站） | 不算我们出网 |
| 服务器返回结果 | **出网** | **约 8 KB** | JSON：title/tags/options/cover/video_url |
| size_probe（HEAD） | 入网 | < 1 KB | 只拿 Content-Length |

**关键**：出网只有 8 KB。**这是 3M 带宽只需要承载的东西。**

**缓存**：`CACHE_TTL=600`（10 分钟），内存 dict，上限 2000 条（超了清过期的）。
两条相同链接 10 分钟内只抓一次。

**批量** `POST /api/batch`：串行解析 N 条（免费上限 3 / 会员 10，硬上限 10），
每条的流量同单条。

---

### ② 保存视频 `wx.downloadFile`（**不经过服务器**）

```
小程序/App → 平台 CDN → 用户手机
```

| 项 | 值 |
|---|---|
| 服务器出网 | **0 字节** |
| 服务器入网 | **0 字节** |
| 25 MB / 100 MB 视频 | 对服务器完全无影响 |

⚠️ **前置条件**：平台 CDN 域名必须在微信后台的 `downloadFile 合法域名` 里。
这是唯一的技术门槛（详见 §5.3）。

---

### ③ 封面显示 `/api/proxy-cover`

| 阶段 | 方向 | 数据量 |
|---|---|---|
| 服务器抓平台图 | 入网 | 约 100 KB |
| 服务器返回图 | **出网** | 约 100 KB |
| 磁盘缓存 | — | `server/media/covers/{sha1前24}.img` |

- 上限 `_COVER_MAX_BYTES = 5 MB`
- 缓存命中后不再抓平台（按 URL hash）
- **为什么需要代理**：小程序 `<image>` 对部分平台 CDN 会裂图（防盗链/域名）

⚠️ 封面是**每个结果页都会加载**的，所以它的出网量（100 KB）比解析 JSON（8 KB）大 12 倍。
日活 3000、每人看 2 个结果页 → 每天 6000 次 → 出网 600 MB/天（如果全部未命中缓存）。
实际大部分会命中缓存。

---

### ④ PDF 工具 `/api/pdf/*`（**双向大流量，且吃内存**）

| 端点 | 做什么 | 返回 |
|---|---|---|
| `/api/pdf/merge` | 2~5 个 PDF 按序拼接 | `{ok, url}` |
| `/api/pdf/extract` | 抽单页 | `{ok, url}` |
| `/api/pdf/watermark` | 加水印文字 | `{ok, url}` |

**完整链路**：

```
客户端上传 PDF（入网，单文件 ≤10MB × 最多 5 个 = 50MB 最坏）
  → 服务器 await f.read() 【全部读进内存】
  → pypdf 处理
  → 存 server/media/pdf/{uuid}.pdf（磁盘）
  → 返回 /media/pdf/{uuid}.pdf
客户端再下载该 URL（出网，最坏 50MB）
  → 24 小时后后台任务自动清理
```

| 项 | 最坏值 |
|---|---|
| 入网 | 50 MB / 次 |
| **内存峰值** | **50 MB+ / 次**（全读进内存 + pypdf 副本） |
| 出网 | 50 MB / 次 |
| 磁盘 | 50 MB / 次，24h 后清 |

⚠️⚠️ **风险：PDF 端点目前完全没有限流**（读码确认）。
如果 10 个人同时传 5 个 10MB 文件 → 峰值内存 500MB+。
2G 内存会被压得很紧，且没有保护。

**这是部署前必须补的**（见 §5.4）。

---

### ⑤ m3u8 合并 `/api/merge`（**客户端未接入**）

| 项 | 说明 |
|---|---|
| 做什么 | 服务器下载 m3u8 分片 → ffmpeg 合并成 mp4 |
| 有流量吗 | 会（入网几十 MB），**但客户端没调用** |
| 客户端调用 | 小程序 ❌ / Flutter ❌（读码确认） |
| 返回内容 | 只返回 `{ok, path, size}`，**不返回文件** |

**结论：这条链路目前不产生真实流量**，但服务端有能力。
如果以后客户端接上，它是第二大流量源（且 CPU 密集，ffmpeg 纯 remux）。

---

### ⑥ 纯数据库类（几乎无流量）

| 端点 | 数据量 |
|---|---|
| `/api/user/login`、`/api/user/quota*` | < 2 KB |
| `/api/member/redeem`、`/api/points/*` | < 2 KB |
| `/api/library/add|list|delete` | < 5 KB |
| `/api/banned/check` | < 10 KB（词库在服务端） |
| `/api/health*`、`/api/capabilities`、`/api/visibility` | < 5 KB |
| `/api/ads/config`、`/api/admin/*` | < 5 KB |

全部走 SQLite（`server/data/cb.db`，当前 316 KB）。

---

### ⑦ 静态文件 `/media/*`

- `/media/covers/*`：封面缓存（服务端生成）
- `/media/pdf/*`：PDF 产物（24h 清理）
- `/media/ads/*`：广告图（运营上传，≤2MB）

由 FastAPI 的 `StaticFiles` 直接下发。

---

## 3. 汇总：谁产生流量

| 来源 | 频率 | 入网 | 出网 | 备注 |
|---|---|---|---|---|
| **解析** | 高 | 150~800 KB | **8 KB** | 高频但出网极小 |
| **封面代理** | 中 | 100 KB | **100 KB** | 有磁盘缓存 |
| **PDF 工具** | 低 | 最坏 50 MB | **最坏 50 MB** | ⚠️ 无限流、吃内存 |
| 视频保存 | 高 | **0** | **0** | 客户端直连 CDN |
| merge | 0（未接） | — | — | 客户端没调用 |
| 数据库类 | 高 | ~2 KB | ~5 KB | 忽略 |

**结论**：
- 出网的**主要来源其实是「封面代理」**，不是解析
- **PDF 是最大的不确定性**（低频但单次极大）
- 视频完全不占服务器

# 第二部分：资源需求

## 1. 内存

| 项 | 实测/估算 |
|---|---|
| 服务进程（1 worker，全模块加载） | **60 MB**（实测） |
| 全部 python 进程 | 101 MB（实测，含健康检查等） |
| 内存缓存（≤2000 条，TTL 600s） | 最多约 10~20 MB |
| SQLite 连接 + 页缓存 | 约 50 MB |
| **PDF 峰值（单次最大）** | **+50 MB**（⚠️ 无限流） |
| **PDF 并发 10 次** | **+500 MB**（❌ 会压垮 2G） |
| **基线合计** | **约 200 MB** |
| **2G 可用余量** | **约 1.8 GB** |

**结论**：日常占用极低，**唯一风险是 PDF 并发**。

## 2. 磁盘

| 项 | 占用 |
|---|---|
| Ubuntu 22.04 + 宝塔面板 | 约 8~10 GB |
| Python 3.10 + 依赖（含 pypdf/imageio-ffmpeg） | 约 800 MB |
| 项目代码 | 15 MB |
| SQLite（含 WAL） | 当前 316 KB，10 万用户估 50 MB |
| `media/covers` 缓存 | 每条约 100 KB，5000 条约 500 MB |
| `media/pdf` 产物 | 24h 内累积，最坏 50MB × N 次 |
| 日志 | **不轮转的话 1~3 GB/月** |
| **合计（首月）** | **约 12 GB** |
| **40G 余量** | **约 28 GB** |

## 3. 带宽（3M = 384 KB/s 速率上限）

| 场景 | 瞬时速率 | 占 3M |
|---|---|---|
| 解析（8 KB/次，峰值 0.17 次/秒） | 1.3 KB/s | 0.35% |
| 封面（100 KB/次，未命中缓存时） | 峰值约 20 KB/s | 5% |
| PDF 下载（50 MB/次） | **打满 384 KB/s，需 133 秒** | 100% |
| **3M 天花板** | **48 次/秒解析** | — |

**结论**：解析 + 封面完全够。**PDF 大文件下载会短暂打满带宽**（但单用户 133 秒可接受）。

## 4. 容量规划：600G 流量能撑多少用户（关热榜后）

### ⭐ 先算一笔：3M 带宽跑满一个月能传多少

```
3 Mbps = 384 KB/s
384 × 86400 秒 × 30 天 = 949 GB/月
```

**你的 600G 流量包 = 相当于「全天平均占用 63% 带宽」。**

而工具类应用的实际带宽利用率通常只有 10~30%。按每天高峰跑满算：

| 每天高峰跑满 | 月出网 | 用掉 600G 的 |
|---|---|---|
| 2 小时 | 79 GB | 13% |
| 4 小时 | 158 GB | 26% |
| 8 小时 | 316 GB | 53% |
| 24 小时 | 949 GB | ❌ 超包 |

**结论：600G 大概率用不完。真正的约束是 3M 带宽。**

### 单次「解析 + 看结果页」的出网量

| 封面方案 | JSON | 封面 | 合计 |
|---|---|---|---|
| 现状均值（实测 30/55/651KB） | 8 KB | 245 KB | **253 KB** |
| 封面压缩后（目标 30KB） | 8 KB | 30 KB | **38 KB** |

⚠️ **封面代理目前是原图转发、零压缩**（读码确认 `_fetch_cover_sync` 只做大小上限检查）。
B站原图实测 **651 KB**，比抖音（30KB）大 20 倍。**封面是出网的最大来源。**

### 两个约束分别对应的日活上限

假设：晚高峰 3 小时承载全天 50% 的浏览量，每人每天 2 次。

| 封面方案 | 带宽约束（3M） | 流量约束（600G） | 谁先卡 |
|---|---|---|---|
| 现状（253KB/次） | **≈ 1.6 万日活** | ≈ 4.1 万日活 | **带宽** |
| 压缩后（38KB/次） | **≈ 10.9 万日活** | ≈ 27.6 万日活 | **带宽** |

**⭐ 结论：无论哪种，3M 带宽都是先卡的，600G 流量用不完。**

### 所以扩容优先级是（不是买流量）

| 优先级 | 动作 | 效果 |
|---|---|---|
| **P0** | **封面压缩**（代理时缩到 360px 宽 + webp） | 单次出网 253KB → 38KB，**容量涨 6.6 倍** |
| P1 | 封面加客户端缓存头 | 小程序端重复访问不再请求 |
| P2 | 升带宽（3M → 5M/10M） | 线性提升，但 10M 以上单价跳档 |
| — | 加流量包 | **基本不需要**，600G 撑日活 4 万+ |

# 第三部分：宝塔部署方案

## 1. 系统与面板

```bash
# 系统：Ubuntu 22.04 LTS（宝塔对 22.04 支持最好）
# 内存 2G，建议加 2G swap 兜底（防 PDF 峰值 OOM）
fallocate -l 2G /swapfile && chmod 600 /swapfile
mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab

# 装宝塔（官方脚本）
wget -O install.sh https://download.bt.cn/install/install-ubuntu_6.0.sh
bash install.sh ed8484bec
```

**宝塔装完后只装这些**（2G 内存别装一堆）：

| 组件 | 装不装 | 理由 |
|---|---|---|
| Nginx | ✅ 必装 | 反代 + HTTPS + 静态文件 |
| MySQL | ❌ 不装 | 项目用 SQLite，装了白吃 300MB+ |
| PHP | ❌ 不装 | 用不到 |
| phpMyAdmin | ❌ 不装 | 用不到 |
| Redis | ❌ 不装（可选） | 单 worker 用内存缓存就够；多 worker 才需要 |
| Python 项目管理器 | ✅ | 宝塔自带，管 uvicorn 进程 |

## 2. Python 环境

宝塔 → 软件商店 → **Python 项目管理器** → 安装 Python 3.10。

```bash
# 或用命令行（宝塔的 python 在 /www/server/pyporject_evn/）
cd /www/wwwroot/creatorbox/server
/www/server/pyporject_evn/versions/3.10/bin/pip install -r requirements.txt
```

### ⚠️ Playwright：装了包可以，但**绝对不要装浏览器**

`requirements.txt` 里确实有 `playwright>=1.45`，装 Python 包本身只占约 40MB，可以装。

**但绝对不要执行 `playwright install chromium`** —— 那会拉 400MB 浏览器，
且 2G 内存跑不动（Chromium 每个实例 400~500MB）。

### 好消息：核心解析完全不依赖 playwright

| 文件 | import 方式 | 影响 |
|---|---|---|
| `parsers/bilibili.py`、`parsers/douyin.py` | **顶层 import** | 但 **pool 不用这两个**（用的是 `_pure` 版） |
| `app/trending.py:363` | **函数内懒加载** | 只有调 `/api/trending` 且走小红书路径才触发 |
| `parsers/signed_platforms.py` | 顶层 import | 但**没有被 pool 装配**（小红书走 `xiaohongshu_pure.py`） |

所以：
- **核心解析（抖音/B站/快手/小红书/百度/微博/搜狐/AcFun）全部走纯 HTTP，不需要浏览器**
### ⚠️ 别把「小红书解析」和「小红书热榜」混为一谈

这两个是**完全不同的链路**，一个不需要浏览器，一个必须需要：

| 功能 | 实现 | 需要浏览器？ | 2G 机器能跑？ |
|---|---|---|---|
| **小红书单条笔记解析** | `xiaohongshu_pure.py`（纯 `urllib`） | ❌ **不需要** | ✅ **能** |
| 小红书热榜（热点词条） | `trending.py:342`（Playwright） | ✅ 需要 Chromium | ❌ **不能** |

**实测（2026-10-23，纯 HTTP、无浏览器、无 Cookie）**：
- 图文笔记 → ✅ 解析成功（标题 + 7 张图）
- 视频笔记 → ❌ 部分失败（页面返回 notFoundPage，是 token/权限问题，跟浏览器无关）

**热榜为什么非要浏览器**（`trending.py` 注释原文）：
> edith 接口要 Cookie **和** x-s 签名（实测无签名 406，纯 HTTP 逆向签名
> 是持久战且随版本失效）。页面自己的 JS 会算好签名发 XHR ——
> 无头浏览器注入 Cookie 打开 explore，拦截自家 XHR 响应即可，**不碰签名算法**。

也就是说：**热点榜是为了绕开 x-s 签名才用浏览器**，不是为了渲染页面。
而且它还额外要求配置 `CB_XHS_COOKIE`（登录 Cookie），没配直接报 `NeedCookieError`。

**建议**：2G 机器上把热榜的小红书 tab 关掉（或前端不展示）。
**小红书解析照常可用**，不受影响。

## 3. 启动方式（关键：单 worker）

**宝塔 Python 项目管理器配置**：

| 项 | 值 |
|---|---|
| 项目路径 | `/www/wwwroot/creatorbox/server` |
| 启动方式 | `uvicorn` |
| 启动文件 | `app.main:app` |
| 端口 | `8080`（只监听 127.0.0.1） |
| **worker 数量** | **1**（⚠️ 见下方说明） |
| 运行方式 | uvicorn |

### ⚠️ 为什么必须 1 个 worker

项目的两个核心组件都是**进程内状态**：

| 组件 | 位置 | 多 worker 的后果 |
|---|---|---|
| `Cache._mem` | `app/cache.py:14` | 请求打到不同 worker → 缓存命中率掉到 1/N |
| `RateLimiter._hits` | `app/cache.py:78` | 每个 worker 独立计数 → 实际限流变成 N 倍 |
| `SingleFlight._inflight` | `app/main.py:427` | **防风控能力失效**（见下） |

### ⚠️ 最严重的是 SingleFlight 失效（不只是性能）

它的作用是：一条链接缓存过期瞬间几十个用户同时请求时，
**只让第 1 个真正抓平台，其余挂起等同一个结果** —— 平台只看到 1 次请求。

多 worker 后，同一个链接的并发请求被分到不同 worker，
每个 worker 都各自抓一次平台 —— **这正是触发平台风控的典型姿势**。

所以单 worker 不只是"缓存命中率高一点"，是**安全设计的一部分**。

**要开多 worker，必须先把缓存和限流换成 Redis**（`CB_REDIS_URL`）。
2C2G 阶段没必要，**单 worker + asyncio 足够**（实测 5 并发 2.8 秒全成功）。

启动命令：
```bash
cd /www/wwwroot/creatorbox/server
CB_API_KEY=$(cat .api_key) \
/www/server/pyporject_evn/versions/3.10/bin/uvicorn app.main:app \
  --host 127.0.0.1 --port 8080 --workers 1 \
  --proxy-headers --forwarded-allow-ips='127.0.0.1'
```

`--proxy-headers` 必须加：否则日志里全是 Nginx 的 IP，看不到真实用户 IP。

## 4. Nginx 反代配置

宝塔 → 网站 → 添加站点 → 反代到 `http://127.0.0.1:8080`。

手动改配置（宝塔生成的配置要补这些）：

```nginx
server {
    listen 80;
    server_name 你的域名.com;
    return 301 https://$server_name$request_uri;
}

server {
    listen 443 ssl http2;
    server_name 你的域名.com;

    ssl_certificate     /www/server/panel/vhost/cert/你的域名.com/fullchain.pem;
    ssl_certificate_key /www/server/panel/vhost/cert/你的域名.com/privkey.pem;

    # ⭐ PDF 上传：默认 1M 会 413，必须放大
    client_max_body_size 60m;
    # PDF 处理慢，超时给足
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;

    # 静态文件直出（不经 FastAPI，省内存）
    location /media/ {
        alias /www/wwwroot/creatorbox/server/media/;
        expires 1d;
        add_header Cache-Control "public";
    }

    # 管理后台也可以由 Nginx 直出
    location = /admin {
        alias /www/wwwroot/creatorbox/server/admin/index.html;
        default_type text/html;
    }

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

⚠️ **`client_max_body_size 60m` 是必须的**：PDF 上传最多 50MB，默认 1M 会直接 413。

## 4.5 域名选择（.top / .site 能不能用）

### 直接回答：能备案，但微信侧风控更严

| 层面 | .top | .site | 结论 |
|---|---|---|---|
| **工信部可备案后缀白名单** | ✅ 在列 | ✅ 在列 | 都能备案 |
| 微信小程序服务器域名 | ⚠️ 可用但风控更严 | ⚠️ 同左 | 见下 |
| 微信分享/落地页 | ⚠️ 容易被拦 | ⚠️ 同左 | 不建议 |

**依据**：工信部「中国互联网域名体系」公示的获批后缀列表里同时包含 `.SITE` 和 `.TOP`
（同列表还有 .XYZ / .VIP / .CLUB / .SHOP / .WANG 等）。
不在该列表的后缀（如 .io / .ai / .cc）**无法备案**，也就无法用于国内服务器。

### ⚠️ 但有三个坑，不是"能备案"就没事

**坑① 注册商必须是中国大陆的获批机构**

这是备案的硬前提，不是微信的限制：
- 在 GoDaddy / Namecheap 注册的 `.top`，**根本备不了案**
- 必须转到阿里云 / 腾讯云 / 新网等工信部批准机构，并完成实名认证

**坑② 微信风控对"新顶级域"更严格**

腾讯云社区与微信开放社区的公开说明都提到：`.top`、`.xyz` 这类新型后缀
"无法充分核验域名主体及安全性，风控审核标准更严格"，可能触发：
- **白色拦截**：提示「如需浏览，请长按复制链接到浏览器」（用户不能在微信内直接打开）
- **新备案域名 15 天观察期**：刚备案的域名会被临时监测，可能出蓝色警告

⚠️ 这些**不是硬性禁止**，是概率性的风控。但一旦触发，申诉周期 3~7 个工作日。

**坑③ 备案主体必须与小程序主体一致**

个人小程序 → 域名必须个人备案；企业小程序 → 必须企业备案。
主体不一致会被驳回。

### 我们的场景：影响比想象中小

我们用的是 **API 域名**（`wx.request` / `wx.downloadFile` 指向的地址），
**不是对外分享的落地页**。小程序的服务器域名只在 App 内部请求，不经过微信的链接传播链路。

所以：
- `.top` / `.site` 作为 **API 域名**：风险较低，基本能用
- 如果以后要做 **H5 分享页 / 落地页**：务必换 `.com` / `.cn`

### 推荐顺序

| 优先级 | 后缀 | 理由 |
|---|---|---|
| 1 | `.com` | 认知度最高，风控最松，几十块/年 |
| 2 | `.cn` | 国家级后缀，备案路径最清晰 |
| 3 | `.top` | 便宜（几块/年），能备案，但风控略严 |
| 4 | `.site` | 同 .top，认知度更低 |

**预算允许就直接 `.com`** —— 域名一年几十块，相比备案 + 审核 + 申诉的时间成本，这点钱不值得省。

### ⚠️ 顺带一个容易漏的点：证书要覆盖域名

Let's Encrypt 申请证书时域名必须已经解析到这台服务器（DNS 验证）。
备案期间域名可能不能解析到国内服务器 → **先在备案前把域名解析到香港验证机测试，
备案通过后再切回国内**（或者用 DNS-01 方式申请证书，不需要服务器）。

## 6. 安全配置

| 项 | 设置 |
|---|---|
| 防火墙 | 只开 22 / 80 / 443，**8080 不对外** |
| `CB_API_KEY` | 必须设（否则管理接口 503 锁死） |
| 宝塔面板端口 | 改默认 8888，加 IP 白名单 |
| SSH | 禁 root 密码登录，改密钥 |
| 数据库 | SQLite 文件权限 640，属主 www |

## 7. 日志轮转（必做）

宝塔 → 计划任务 → 添加 Shell 脚本：

```bash
#!/bin/bash
# 每天凌晨清理 14 天前的日志
find /www/wwwroot/creatorbox/server/logs -name "*.log" -mtime +14 -delete

# 清理 3 天前的封面缓存（按需，缓存可重建）
find /www/wwwroot/creatorbox/server/media/covers -name "*.img" -mtime +3 -delete
```

或直接配 logrotate：

```bash
cat > /etc/logrotate.d/creatorbox <<'EOF'
/www/wwwroot/creatorbox/server/logs/*.log {
    daily
    rotate 14
    compress
    missingok
    notifempty
    copytruncate
}
EOF
```

## 8. 备份（必做）

宝塔 → 计划任务 → 备份数据库：

```bash
#!/bin/bash
# 每天备份 SQLite（热备，用 .backup 命令安全）
DATE=$(date +%Y%m%d)
mkdir -p /www/backup/db
sqlite3 /www/wwwroot/creatorbox/server/data/cb.db \
  ".backup /www/backup/db/cb-$DATE.db"
find /www/backup/db -name "cb-*.db" -mtime +30 -delete
```

⚠️ **不要直接 `cp` SQLite 文件**（可能正在写入，拷到半个文件）。
必须用 `sqlite3 .backup` 或 `VACUUM INTO`。

# 第四部分：必须做的加固（部署前）

## 1. 🔴 PDF 端点加限流（最高优先）

**现状**：`/api/pdf/*` 完全无限流（读码确认）。
一个用户狂传 50MB 文件就能把 2G 内存打满。

**改动**（`server/app/main.py`）：

```python
# 在 api_pdf_merge / api_pdf_extract / api_pdf_watermark 开头加：
ok, info = await limiter.allow(f'pdf:{request.client.host if request.client else "unknown"}')
if not ok:
    raise HTTPException(429, f'PDF 处理过于频繁，请 {info["retry_after"]}s 后重试')
```

外加并发闸（同时只允许 2 个 PDF 任务）：

```python
_pdf_sem = asyncio.Semaphore(2)

async with _pdf_sem:
    ...  # 实际处理
```

**理由**：PDF 是唯一能在单次请求里吃掉 50MB 内存的接口，
而 2G 内存下 10 并发就危险。限流 + 信号量是最小成本保护。

## 2. 🟡 curl 版本健康检查不要打太频繁

`/api/health` 会触发真实探针（抓平台）。宝塔监控如果 1 分钟一次，
会持续产生入网流量。建议 **5 分钟一次**。

## 3. 🟡 封面缓存定期清理

`media/covers` 会一直增长（每条 100KB）。配 cron 清 3 天前的。

## 4. 🟢 关掉不需要的平台

如果只做国内，设 `CB_INTL_ENABLED=0` 关掉 YouTube/TikTok 等国际平台，
减少探针和无谓抓取。

# 第五部分：待你确认的事

## 1. 微信 downloadFile 白名单（P0，影响能否保存）

各平台 CDN 域名必须加进小程序后台的 **downloadFile 合法域名**：

```
抖音：n98-v-ncdncold.douyinvod.com 等（编号可能随视频变）
B站：cn-hbyc-ct-01-01.bilivideo.com 等（含地域+运营商前缀）
百度：vd3.bdstatic.com
```

⚠️ 微信**不支持通配符**。B站那种带地域前缀的域名，换个地区可能就变了。

**这个必须你到小程序后台确认实际配了什么**，否则用户点保存会失败。

## 2. 宝塔面板要不要装

宝塔会占约 200~300MB 内存 + 一定磁盘。
2G 内存下装宝塔 + 项目，日常约 500MB，够用。

**但要接受**：宝塔本身是个 Web 服务，也多一个被攻击面。
如果你只需要部署，用 systemd + 纯命令行更轻（省 300MB）。

**我的建议**：装宝塔。你有运维需求（看日志、改配置、备份），
宝塔的可视化能省很多时间，300MB 在 2G 里换得起。

## 3. 域名与备案

- ECS 包年 ≥3 个月可以备案
- 备案期间域名不能解析到国内服务器（否则被拦）—— **备案期建议先用 IP + 端口测试**
- HTTPS 证书要在域名解析生效后申请
