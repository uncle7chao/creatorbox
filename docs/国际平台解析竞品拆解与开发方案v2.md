## 二、Evil0ctal v4 深度拆解（TikTok 主方案）

### 2.1 v4 架构（2026 重构，src/dtk/）

```
dtk/
├── platforms/{tiktok,douyin,bilibili,...}/
│   ├── endpoints.py   端点 URL 表（P0 端点 + 全量常量）
│   ├── params.py      每端点参数构造（含 profile：guest/session）
│   ├── parser.py      响应 → 结构化模型（Content/Author/Page）
│   └── adapter.py     平台适配器（registry 发现机制）
├── signing/native/tiktok_sign.py   纯 Python TikTok 签名（755 行）
└── api/                FastAPI + API Key + 代理池 + 管理端
```

### 2.2 ⭐ TikTok 纯 Python 签名（755 行，字节级验证 2026-09-08）

- **算法本质**：`payload = TLV([key][0x00][len][value...])` → **ChaCha-like keystream XOR**（轮数 = 5 + Σ(key&0xF)&0xF，per-call 12 个随机 uint32）→ **48 字节密钥按 (Σkey+Σcipher) % (len+1) 拼接进密文** → 自定义 base64（前缀 \x4b）
- **签名自带密钥**——服务端能解密校验，这也是为什么两两次签名字节不相等（无法缓存复用，必须每次现场算）
- **许可纯净**：Evil0ctal 注释明确声明——JoeanAmier 版是 GPL-3.0（抄了会传染许可证）、xvhuan 版 MIT+附加限制自相矛盾（GitHub 判 NOASSERTION）——**这个移植版直接逆向自平台 JS bundle，无第三方版权**，且项目整体 Apache-2.0
- **与我们的血缘**：我们抖音 a_bogus 就来自该项目（Apache-2.0，出处声明已留）——**同源引用合法且顺理成章**

### 2.3 ⭐⭐ Guest Identity 免登录（决定性发现）

`params.py` 多处实测注记（2026-09-13）：
- **「铸造的 guest identity、无任何 session cookie，读到的数据与登录态一致」**——content detail / author posts / collections / comments 多端点验证
- msToken/_signature 由签名模块处理，不需要浏览器环境
- 风控检测内建：`detect_risk_control(payload)` 识别验证码/限流响应

**结论**：TikTok 接入不再需要 tikwm 第三方 API 或 Cookie 池——**vendor Evil0ctal 的 dtk TikTok 模块（约 2400 行，Apache-2.0）即可自持**。

### 2.4 覆盖能力（远超单视频解析）

content detail / author posts / likes / bookmarks / collections / reposts / comments+replies / mixes / live 端点全表——**账号级批量采集能力**是 tikwm 没有的。TikTok 卖家场景（下载自己账号全部带货视频做复盘）直接可用。

## 三、X/Twitter：三层降级架构（nuncij MIT 范本）

463 行 Node 项目的架构值得整段学习：

```
层1 yt-dlp -J（主力）：guest-token 流由它维护，formats 全量+文件大小，1-2s
层2 FxTwitter API（api.fxtwitter.com/status/{id}）：免鉴权 JSON，200-300ms，
    补 yt-dlp 缺口：photo-only 推文和 GIF yt-dlp 不返回
层3 失败降级：一家挂了另一家顶上，degrade 而非 die
```

**实测运营情报**（该作者踩坑记录）：
- **Progressive MP4（音视频合体单文件）最高只有 720P**——1080P 是 HLS 分轨，必须 ffmpeg 合并（15s 片段合并 1.8s）
- **yt-dlp 的 JSON 里 progressive 格式的 vcodec/acodec 是 null**（不是 h264/aac）——按 codec 字段分类会误杀所有好文件，**要按 protocol 分类**（http 开头=合体文件）
- FxTwitter 还支持 `d.fxtwitter.com/user/status/{id}` 直接下载、URL 加 `.mp4` 后缀直出

**我们的实现**：parse-video-py 的 syndication π-token 版（MIT）已拆解 + FxTwitter 作为层2 + yt-dlp 层3，三层结构成本 1.5 天。

## 四、YouTube：yt-dlp 引擎 + 三个运营情报

来源：Universal-Video-Downloader 的 2026 实测排障表（最具时效性）：

1. **YouTube 新格式需要 JS 运行时**：「No supported JavaScript runtime」警告会丢清晰度——**装 Deno 或 Node.js** 自动识别（nsig 挑战要用）
2. **yt-dlp 必须 ≥2026.08.19 级别**——YouTube 对抗靠版本追，**每月 pip -U yt-dlp 进运维例行**
3. cookies 有时需要（年龄限制内容）——Netscape 格式 cookie 文件按平台命名管理

**IP 锁问题维持 v1 判断**：googlevideo 直链绑定请求 IP，小程序 302 不可靠 → 解析信息小程序可见、文件下载放扩展端（App 端用 youtubedl-android 在用户设备上跑，IP 一致）。

**Android 端直接复用**：`youtubedl-android`（0.18.1）= yt-dlp 的 Android 封装库，Seal/KDownloader 都基于它——我们 Flutter App 端 YouTube 下载开箱即用（含 SHA-256 校验内置二进制）。

## 五、Facebook：2025 年后的现实（运营情报）

Universal-Video-Downloader 排障表给出 FB 的 2026 现状：

1. **FB 改版频繁，几乎总要 Cookie**（`www.facebook.com_cookies.txt`）
2. **yt-dlp 需装 `yt-dlp[default,curl-cffi]`**——curl-cffi 浏览器伪装是 FB 解析的硬要求（2025 起）
3. 新鲜 Cookie 是生命线（旧 Cookie 报「Cannot parse data」）
4. Reels 需要 CORS 代理；Threads 更麻烦（要 headless Chrome）

**结论**：FB = yt-dlp + curl-cffi + Cookie 池三件套，是四平台里运维最重的。维持 P3 spike 定位。
