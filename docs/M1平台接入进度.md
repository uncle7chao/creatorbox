## 🔧 m3u8 合并服务（2026-10-05 第十四轮增补）

用户决定引入 ffmpeg 解决「只有 m3u8」问题。

### 落地方式：零外部依赖

用 `imageio-ffmpeg` pip 包 —— **它自带静态编译的 ffmpeg 二进制**，
装上就能用，不需要运维手动装 ffmpeg。

```
pip install imageio-ffmpeg   →  83.6 MB 二进制
ffmpeg version 7.1-essentials_build-www.gyan.dev
能力: libx264 ✅ aac ✅ mp4 muxer ✅ faststart ✅ tls ✅
```

四级回退：`CB_FFMPEG_PATH` → 系统 PATH → 常见安装路径 → pip 包自带。

### ⚠️ 许可必须注意

imageio-ffmpeg 的二进制是 **GPL 构建**（实测 `--enable-gpl`）：

| 用法 | 风险 |
|---|---|
| **子进程调用**（我们的做法） | 通常不构成衍生作品，商用风险低 |
| 静态链接进自己的二进制 | **触发 GPL 传染** |
| 打进单文件可执行 | **触发 GPL 传染** |

→ 代码与二进制解耦，可用 `CB_FFMPEG_PATH` 换成合规版本。
**上线前请法务确认**，或镜像里改用 `apt install ffmpeg`。

### ⭐ 核心：`-c copy` 纯 remux，不转码

m3u8 分段本身已是 H.264+AAC，ffmpeg 只需重封装。

| 指标 | 实测值 |
|---|---|
| 耗时 | **5.36 秒**（150MB / 299 秒视频） |
| 产物体积 | 150.04 MB |
| 产物时长 | **299.01s**（源 EXTINF 299.0s） |
| `duration_ratio` | **1.0**（完全一致） |
| faststart | ✅ 生效 |
| 抽帧验证 | 5s 与 150s 两帧内容完全不同 → 真实完整视频 |

`-movflags +faststart` **必须加** —— 否则 moov 在文件尾，
移动端要下完整个文件才能播。

### 🔴🔴 最重要的发现：搜狐的 m3u8 **也是试看片段**

我本来以为「引入 ffmpeg 就能解决搜狐长视频」。**实测发现不能。**

搜狐 m3u8 声称：12 段、EXTINF 合计 76.85s。看起来像完整视频。

| 检查 | 结果 |
|---|---|
| 各段 MD5 | **12 段完全相同**（`f978b015...`） |
| 每段真实时长 | 全部 30.02s |
| ffmpeg 合并产物 | **360.04s**（12 × 30s 重复） |
| ffmpeg 退出码 | **0 —— 不报任何错** |

**最阴险的地方**：ffmpeg 只会按 EXTINF 累加时长，
所以它"成功"了，产出一个 6 分钟的垃圾文件，**退出码还是 0**。
如果只看「合并成功」就交付，用户会拿到一个重复 12 遍的视频。

→ 已实现**合并前哈希预检**（P22）：
```python
# 取前 3-4 段算 MD5，若全同 → 判定重复试看片段，直接拒绝
hashes = {md5(_get(segs[i])) for i in range(min(4, len(segs)))}
if len(hashes) == 1:
    return {'ok': False, 'duplicate_segments': True}
```
实测搜狐 **2.28 秒**被正确拒绝，**不产出垃圾文件**。

**结论**：搜狐 >30s 的视频必须登录态才能拿完整版。
已通过 `truncated` + `user_warning` + `m3u8_usable=false` 如实告知。

### 新增接口

```
POST /api/merge    {text: m3u8地址, referer, prefer: auto|direct|segments}
                   → 合并前预检重复段；返回 ok/path/size/duration_ratio
GET  /api/ffmpeg   → 能力自检 + GPL 许可提示（部署自检用）
```

### 两种合并模式

| 模式 | 做法 | 优点 | 实测 |
|---|---|---|---|
| `direct` | ffmpeg 直接拉 m3u8 | 快、不落盘分段 | **AcFun 5.4s ✅** |
| `segments` | 并发下分段(8线程) → concat | 可带任意 header、可重试 | 兜底 |

`prefer=auto` 时先 A 失败降级 B。分段下载并发 8，整体超时 600s，
临时目录 `finally` 必清理（否则并发大时堆满磁盘）。

### 微博踩到的两个坑（新增 P17 / P18）

**P17「第一个元素就是最优」是巧合**
文档原写「urls 的第一个 key 是最高码率」。实测第一个确实是最高档，
但那是 *dict 保序 + 平台按降序插入* 的结果，**不是规律**。
平台一旦调顺序就会取错档 → 改为**从 label 解析高度再排序**。

**P18 用字节串计数判断音轨会误判**
我数 `b'trak'` 出现次数得 1，就断言「疑似无音轨」。
正确做法是**递归遍历 box 树看 hdlr** —— 实际 trak=2（vide+soun），
音轨完好。`trak`/`mdia`/`avc1` 在文件里会多次出现，计数无意义。

### oid 格式（容易踩）

```
1034:5343195622473745
^^^^ ^^^^^^^^^^^^^^^
prefix  media_id
```

**冒号前是 prefix，不是 media_id** —— 不要把整串当纯数字用。
正则：`\b(\d{3,6}):(\d{9,})\b`

### 支持的 4 种链接形态（全部实测通过）

