# 服务器规格评估：2 核 8G / 8M 带宽 / 1000G 流量

> 2026-10-24 · 基于**实测**（不是估算）
> 对比对象：`docs/服务器规格评估-2C2G-40G-3M.md`（最小可用配置）
> 前提：封面压缩已上线（单次出网从 267KB 降到 36KB）

---

## 0. 直接回答

**够，而且对「万级用户」严重过剩。但有两个反直觉的结论：**

> **① 内存从 2G 涨到 8G 并没有解决瓶颈 —— 2 核 + 8M 是「紧配」：
> 8M 跑满时 CPU 要用掉 1.3 核（封面缓存未命中 30%）。**
>
> **② 但这台机器最先卡住的既不是带宽也不是 CPU，而是「每 IP 30 次/分钟」的限流。**
> 压测 40 并发直接被拒 38 个。移动端共享 NAT 出口的场景会误伤真实用户。

| 资源 | 买了 | 实际需求（日活 1 万） | 余量 |
|---|---|---|---|
| 内存 | 8 GB | ~700 MB（含浏览器通道） | **7.3 GB** ✅ 大幅过剩 |
| 带宽 | 8 Mbps | 约 0.1%（日活 1 万） | ✅ 过剩 |
| 流量 | 1000 GB/月 | 约 73 GB/月（日活 1 万） | ✅ 富裕 |
| **CPU** | **2 核** | 0.15 核（日活 1 万） | ✅ 够，但 8M 跑满时会紧 |
| **限流** | 30 次/分钟/IP | — | ⚠️ **共享 IP 场景会误伤** |

## 1. 三个维度的容量上限（谁先卡）

### 单次「解析 + 看结果页」的真实开销（实测）

| 项 | 数值 | 来源 |
|---|---|---|
| 出网 | **36.4 KB**（JSON 8 + 封面 28.4） | 实测三平台均值 |
| 解析 CPU | **25 ms** | 服务进程 CPU 秒差实测（抖音 31ms / B站·百度 <5ms） |
| 封面压缩 CPU | **73 ms**（仅缓存未命中） | PIL draft + webp q80 |

### ① 带宽 8M 能撑多少

```
8 Mbps = 1024 KB/s
1024 ÷ 36.4 KB = 28.1 次/秒 = 1,688 次/分钟 = 101,275 次/小时
```

| 高峰跑满 | 高峰承载 | 全天（高峰占 50%） | 日活（每人 2 次） |
|---|---|---|---|
| 2 小时 | 202,549 次 | 405,099 次 | **20.3 万** |
| 3 小时 | 303,824 次 | 607,648 次 | **30.4 万** |
| 4 小时 | 405,099 次 | 810,198 次 | **40.5 万** |

### ② 流量 1000G 能撑多少

```
1000 GB ÷ 36.4 KB = 28,807,033 次/月
→ 每天 96 万次 → 日活 48 万（每人 2 次）
```

⚠️ **一个容易搞错的关系**：8M 全天 24 小时跑满 = **2531 GB/月**，
而流量包只有 1000 GB → **相当于「全天平均占用 40% 带宽」**。

也就是说：**你不可能同时用满 8M 和 1000G。** 流量包会先耗尽。

### ③ CPU 2 核能撑多少

| 封面缓存未命中率 | 单次 CPU | 2 核吞吐 | 8M 满速需 | 8M 满速时占用 |
|---|---|---|---|---|
| 10% | 32 ms | 61.9 次/秒 | 28.1 次/秒 | **0.91 核** |
| 30% | 47 ms | 42.6 次/秒 | 28.1 次/秒 | **1.32 核** |
| 50% | 62 ms | 32.5 次/秒 | 28.1 次/秒 | **1.73 核** |

⭐ **未命中 50% 时，2 核只剩 0.27 核余量。**

### ④ 实测压测：服务本身能力是带宽需求的 4.6 倍

在开发机（16 核）上压当前的单 worker 服务，**缓存命中路径**：

| 并发 | 结果 | P50 | 吞吐 |
|---|---|---|---|
| 25 | 25/25 成功 | 45 ms | **128 次/秒** |
| 40 | 38 个 429 | — | 被限流拦住（见下节） |

```
8M 带宽需要 28.1 次/秒
实测服务能力 128 次/秒
→ 服务能力是带宽需求的 4.6 倍 ✅
```

⚠️ 这条是**缓存命中**的数据（不抓上游、不压缩）。缓存未命中时要加上
25ms（抓页面）+ 73ms（压缩），所以上面的 CPU 推算（47ms/次）是保守的，
结论不变：**2 核够，但 8M 满速时会用到 1.3 核**。

### ⭐⭐ 结论：先卡的不是带宽，是「每 IP 限流」

```
带宽 8M    ≈ 30 万日活
流量 1000G ≈ 48 万日活
CPU 2 核   ≈ 刚好够 8M 满速
限流        = 每 IP 30 次/分钟  ← 可能最先碰到
```

**限流规则**（读码确认）：
- `ident = request.client.host`（按 IP）
- `CB_RATE_LIMIT` 默认 **30 次/分钟**
- 超了返回 `429 请求过于频繁，请 Ns 后重试`

对单个用户：每天用 2 次，30 次/分钟**远远够**。
但对以下场景**会误伤**：

| 场景 | 风险 |
|---|---|
| 公司 / 学校 / 网吧 共享出口 IP | 10 个人同时用就接近上限 |
| **移动网络运营商 NAT**（最常见） | 一个基站下大量用户共享 IP |
| 压测 / 自动化 | 40 并发直接被拒 38 个（实测） |

**建议（按优先级）**：
1. **登录用户用 `openid` 当限流 key，匿名用户才用 IP** ——
   我们本来就有 openid（`QUOTA.ensureLogin()`），能精确到人，共享 IP 就不误伤了
2. 匿名用户的阈值可以放宽到 60~100 次/分钟（反正有封面缓存，成本低）
3. Nginx 层再加一层 `limit_req`（每 IP 10 次/秒）挡暴力刷

> ⚠️ 这是个**产品可用性风险**，不是性能问题 —— 8M 带宽根本用不完，
> 但用户可能因为「和别人共用 IP」被拒。移动端占大头的小程序尤其要注意。

## 2. ⭐ 8G 内存解锁了什么（对比 2G 的禁区）

之前 2G 机器明确「干不了」的三件事，现在逐个看：

| 能力 | 2G 机器 | **2C8G** | 说明 |
|---|---|---|---|
| **浏览器通道**（小红书热榜） | ❌ 跑不动 | **✅ 能跑，但抢 CPU** | Chromium 400~500MB/实例；8G 装得下 2~3 个 |
| **PDF 高并发** | ❌ 10 并发就危险 | **✅ 内存安全** | 最坏 50MB×N，8G 下 50 并发也不怕；但 CPU / 流量要留意 |
| **视频中转兜底**（need_proxy） | ❌ 不可行 | **⚠️ 只能兜底** | 8M 出网 25MB 视频要 25 秒；1000G 只够 4 万个/月 |

### ① 浏览器通道：内存够了，但**别全时段开**

小红书热榜要 Playwright + Chromium（`trending.py:342`，为绕 x-s 签名）。
8G 内存装得下，但：

- Chromium 一个实例吃 **400~500MB + 持续 CPU**
- 2 核在 8M 满速时已用 1.32 核，**再开 Chromium 会直接过载**
- 还额外需要 `CB_XHS_COOKIE`（没配直接 `NeedCookieError`）

**建议**：热榜功能可以开，但
- 限制并发（`asyncio.Semaphore(1)`，同一时刻只跑一个浏览器实例）
- 只在低峰期跑（热榜本来就有 10 分钟缓存，不需要实时）
- 或者干脆做成「按需触发」而非「页面一打开就抓」

### ② PDF：内存安全了，但**限流仍然必须补**

8G 下 PDF 不再有 OOM 风险（50MB × 50 并发 = 2.5GB，还在安全区）。
但两个问题没解决：

- **CPU**：pypdf/reportlab 是纯 CPU 密集，一次合并能吃几百 ms
- **流量**：每次最坏 50MB 出网 → 1000 次 = **50GB**（占 1000G 的 5%）

**PDF 端点目前完全没有限流**（读码确认：没有 `limiter.allow()`，没有 `asyncio.Semaphore`）。
8G 内存让它从「会崩」降级为「会慢 + 吃流量」，但**仍然该补限流**。

## 3. 部署配置要改的地方（对比 2C2G 方案）

| 项 | 2C2G 方案 | **2C8G 方案** | 原因 |
|---|---|---|---|
| swap | 2 GB（防 PDF OOM） | **1 GB 或不配** | 8G 内存够，swap 只是保险 |
| uvicorn worker | **必须 1** | **仍然必须 1** | 见下（原因不变） |
| playwright chromium | ❌ 不装 | ✅ 可装，限并发 | 内存够了 |
| 小红书热榜 | ❌ 关掉 | ⚠️ 可开，限并发 + 低峰 | CPU 要留余量 |
| Nginx `client_max_body_size` | 60m | 60m（不变） | — |
| 日志轮转 | 必须 | **仍然必须** | CPU/内存无关 |
| 封面缓存 cron | 建议 | 建议（单条只有 10~50KB 了） | — |

### ⚠️ 单 worker 这条**没有变**，改的是别的东西

```python
# 仍然必须 --workers 1
# 原因和内存无关，是【进程内状态】：
#   Cache._mem        (cache.py:14)   → 多 worker 缓存命中率掉到 1/N
#   RateLimiter._hits (cache.py:78)   → 多 worker 限流变 N 倍（等于没限）
#   SingleFlight      (main.py:427)   → 防风控失效（这条最严重）
```

`SingleFlight` 的作用是「一条链接爆了时只让 1 个请求抓平台，其余等同一结果」。
多 worker 后每个 worker 各抓一次 —— **这正是触发平台风控的典型姿势**。

**2 核下开 2 worker 不会更快**：Python GIL 让单个进程的字节码只用 1 核，
真正的并行来自 C 扩展（PIL 压缩释放 GIL）和阻塞 IO（线程池里）。
开 2 worker 只会把缓存/限流切碎，换不来性能。

> 什么时候才考虑多 worker：日活过 5 万、且把 cache/limiter 换成 Redis
> （`CB_REDIS_URL`）之后。现在不需要。

### 具体配置

```bash
# 1. swap（8G 下可选，保险起见给 1G）
fallocate -l 1G /swapfile && chmod 600 /swapfile
mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab

# 2. uvicorn 启动（单 worker，线程数不用调）
uvicorn app.main:app --host 127.0.0.1 --port 8080 --workers 1

# 3. 如果开浏览器通道，必须限并发（代码层）
#    trending.py 里加 asyncio.Semaphore(1)
```

## 4. 采购与运营：三件必须确认的事

### ⚠️ ① 1000G 用完了会怎样（最关键）

轻量服务器的带宽是「固定峰值 + 月流量包」，**流量包用尽是硬上限**。不同厂商处理不同：

| 处理方式 | 后果 | 你要做的 |
|---|---|---|
| **限速**（多数情况） | 出网降到 1Mbps 级，服务变慢但不停 | 可接受，但要监控 |
| **按量计费** | 超出部分 0.8 元/GB 左右 | **超 100G 就 80 元**，必须设预算告警 |
| **停服** | 直接断网 | 最坏情况，不能接受 |

**必须问清销售：流量包用尽后是限速、按量计费、还是停服？能否开启「用尽即限速」模式？**

### ⚠️ ② 会不会被刷爆流量

`/api/parse` 是**无鉴权**接口（游客可用）。封面缓存能省「上游抓取 + CPU」，
但**省不了「我们到用户的出网」** —— 缓存命中照样要发 28KB 给客户端。

- 一个脚本刷 1000 次解析 = **36 MB** 出网
- 刷满 1000G 需要 **2800 万次** —— 单机刷不动，但分布式/肉鸡可以
- **轻量没有 DDoS 高防**

**建议**（按优先级）：
1. Nginx `limit_req`（每 IP 10 次/秒）+ `limit_conn`（每 IP 5 连接）
2. 应用层已经有限流（`limiter.allow()`），确认 `/api/parse` 的阈值
3. 到一定规模换 ECS（可挂 DDoS 基础防护）或套 CDN

### ⚠️ ③ 续费价

轻量的活动价通常「限新用户 / 首年」。**让销售书面确认续费价。**

## 5. 值不值得买

### 现状：严重过剩，但买大是对的

```
当前日活：0（还没上线）
2C2G 就能撑到日活 1.6 万
2C8G 能撑到日活 30 万
```

**纯从性能看，现在买 2C8G 是浪费。但有一个理由让它合理：**

> **迁移成本不在钱，在备案。**
> 服务器 IP 变了要走「接入变更」（1~3 个工作日，期间可能影响访问），
> 而且换机器要重新配环境、迁数据、重跑测试。

所以：
- 如果你**确定半年内不会上大量用户** → 2C2G 够，省下的钱不如投到推广
- 如果你**不想半年后折腾迁移** → 2C8G 一次到位，撑到 30 万日活，合理

### 我的建议：买，但把它当「一次到位」

2C8G/8M/1000G 的配置能覆盖你从现在到「日活 10 万」的整个阶段。
唯一需要提前接受的是：**2 核是这套配置里最紧的一环**，
以后要开浏览器通道或做视频中转时，CPU 会先叫。

## 6. 什么时候该升级（触发条件）

| 指标 | 阈值 | 动作 |
|---|---|---|
| **用户反馈「请求过于频繁」** | 出现即处理 | **改限流 key（openid 优先）**，见 §1④ |
| CPU 持续 > 70% | 连续 10 分钟 | 优先查是不是封面未命中率高 / 有人在跑 PDF |
| 流量包用到 80% | 月中就 800G | 加流量包，或查是否被刷 |
| 带宽跑满（8M 打满） | 每晚高峰 | 升 12M/16M（单价会跳档） |
| 日活 > 5 万 | — | 换 ECS + Redis + 多 worker，或上 CDN |
| 热榜经常超时 | — | 说明 Chromium 抢 CPU 了，挪到独立机器 |

---

## 7. 一句话总结

> **内存 8G 是完全过剩的（实际用 700MB），流量 1000G 够用到日活 48 万，
> 带宽 8M 够到 30 万日活、服务能力（实测 128 次/秒）是带宽需求的 4.6 倍。
>
> 但这台机器上有三个「比带宽更早卡」的东西，按出现顺序：
> ① **每 IP 30 次/分钟的限流**（共享 NAT 出口会误伤，最该先改）
> ② **2 核 CPU**（8M 跑满时用到 1.3 核，开浏览器通道就会过载）
> ③ **1000G 流量包用尽后的处理方式不明**（限速 / 按量计费 / 停服，必须问销售）
>
> 换句话说：**这台机器不缺内存、不缺流量、暂时不缺带宽 —— 缺的是「确认三件运营细节」。**
