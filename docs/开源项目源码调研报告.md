### ⭐ 关键发现

**① 25 个平台全部不需要签名。** 唯一涉及签名的是 Go 版的 detail 接口（a_bogus）。这与"解析必须逆向签名"的普遍认知相反。

**② 图集平台只有 5 个**：抖音、快手、小红书、皮皮虾、微博。

**③ webp 处理只有抖音/西瓜需要**：源码有 `_get_no_webp_url()` 遍历 `url_list` 取首个非 webp。**小红书不处理 webp，而是换域名 + 强制 `?imageView2/format/jpg` 后缀。**

**④ 美拍用了 base64 混淆**（`meipai.py:46-86`，4 步解码）—— 这是为了绕混淆，其他平台都没有。

**⑤ 两个平台有坑，源码自己标注了**：
- 皮皮虾：`video_high` 可能带水印，源码建议优先取 `comments[].item` 里作者同 ID 的

### ⭐⭐ 最有价值的技巧：抖音清晰度拼接（`douyin-parser.ts:36`）
```ts
const videoUrl = `https://www.iesdouyin.com/aweme/v1/play/
  ?video_id=${item.video.play_addr.uri}&ratio=1080p&line=0`;
```
**思路**：先从 SSR 拿到 `play_addr.uri`（一个短字符串），再自己拼播放接口，`ratio` 参数控制清晰度。

**我实测验证（本日新增）**：
| ratio | 结果 | 体积 |
|---|---|---|
| `1080p` | ✅ **1920×1080** 真实 1080P | 31.9 MB |
| `720p` | ✅ 1280×720 | 23.2 MB |
| `540p` | ✅ 302 成功 | — |

**这解决了 v2 接口的一个硬限制**：`slidesinfo` 返回的 `bit_rate` 数组实测最高只有 `720_3_1`（720P），要 1080P 只能走这个 play 接口。已落地为解析器的 L3 通道。

⚠️ 微博解析器**强制要求 cookie**（`weibo-parser.ts:32` 报错 `'请先设置微博 cookie'`）。

### 下载内核细节
| 项 | 数值 | 来源 |
|---|---|---|
| 分片并发 | `Math.min(cpus().length * 2, **8**)` 上限 8 | `lib/format-options.ts:107` |
| 任务并发 | `maxDownloads` 默认 **3** | `lib/m3u8-download.ts:25` |
| 分片重试 | 3 次（`success >= -3`） | `lib/m3u8-download.ts:283` |
| AES-128 | `createDecipheriv('aes-128-cbc')` | `lib/crypto.ts:44` |
| **SAMPLE-AES** | ❌ **不支持**，非 AES-128 时原样返回密文并 warn（样本级加密套整段解密会损坏数据） | `lib/crypto.ts:13-15,35-41` |
| BYTERANGE | ✅ `Range: bytes=offset-(offset+length-1)`，offset 继承处理 | `lib/utils.ts:25`, `parseM3u8.ts:111-119` |

**ffmpeg 合并两条命令**：
- fMP4：二进制拼 `initSegment + 分片` → `ffmpeg -y -i raw -c copy -movflags +faststart out`（`:127`）

- **兜底** `binaryMerger` 纯二进制拼接不依赖 ffmpeg（`:168`）
- 合并器是**策略模式**，`registerMerger()` 可注册新容器（`:194`）

### ⭐ 重要洞察：小红书/快手为什么不需要签名

**它们根本没调 API** —— 直接 GET 笔记页/短视频页，抓页面内嵌 state：
- 小红书：`window.__INITIAL_STATE__`（`:30`）
- 快手：`window.__APOLLO_STATE__`（`:27`）

⚠️ **这比签名更脆弱**：页面结构一改就失效，快手那个硬编码 cookie 随时会挂。

### 它的抖音签名方式值得注意

`qwen3vl.py`：ffmpeg 抽帧（默认 6 帧）→ base64 → 调 **ModelScope 云端 API**（`api-inference.modelscope.cn`，OpenAI 兼容）。

`Dockerfile:17-26`：`python:3.11-slim` + ffmpeg，**无浏览器、无模型权重** → 内存占用极低。

## 七、VnaSeek / Yeguo-IDM / phlsM3U8 / kitty / TVHelper

### VnaSeek（无 LICENSE，不可商用）
- **平台**：无自研解析器，全部 `yt-dlp`
- **「不落盘」真相**：**是逐字节转发，服务端双倍带宽**
  - `/api/stream/{token}` 返回 `StreamingResponse`（`backend.py:618`），全仓库 **0 处 `RedirectResponse`**
  - `httpx.AsyncClient.send(stream=True)` + `StreamingResponse(response.aiter_bytes(1024*256))`（`:663-664`）
  - 后端同时返回 `directUrl` 和 `proxyUrl`，但前端 `main.js:175` 是 `proxyUrl || directUrl` —— **默认走代理**
  - B站 dash 需下视频+音频两条流，服务端双倍承担
- **前端 FFmpeg.wasm 合并**（`main.js:266-283`）：`-y -i video -i audio -map 0:v:0 -map 1:a:0 -c copy -shortest`，mp4 加 `-movflags +faststart`。**无转码，纯 stream copy**
- ffmpeg 全从 CDN 加载：`@ffmpeg/ffmpeg@0.12.15` + `@ffmpeg/core@0.12.10`（jsdelivr，`main.js:300-301`）
- **对我们是负优化** ——我们要避免中转

### TVHelper（**GPL-3.0，不可商用**）
最巧的设计 —— `api` 字段**双语义**：`type:1` 是 URL，`type:3` 是类名 `csp_XXX`（从 spider jar反射调用）→ **接口地址与解析器实现解耦**。

值得借鉴的 4 点（**只读设计，AGPL/GPL 代码不能抄**）：
1. **订阅链 + 失效切换**（`handler.go:77-143`）：遍历订阅，第一个成功的作主源，后续**合并**进来 → **映射到我们：25+ 平台不该写 25 个 if-else，应是「解析器数组 + 依次尝试」**
2. **源级黑白名单**（`struct.go:26-36`）：白名单非空则只留白名单内，否则才应用黑名单
3. **保序去重**（`utils.go:8-19`）：泛型 + Set
4. **类型宽容解码**（`struct.go:38-81`）：`UnmarshalJSON` 对 bool/string/number 三形态都接受 → **上游字段类型不可信，这个容错值得复制**
5. **源元数据含`Timeout` / `Header`**（`site.go:11-33`）→ 每个平台的超时和 headers 应配置在源上

## 九、已落地到工程的结论

### 抖音三级通道（纯 HTTP）
```
L1  v2 slidesinfo（免cookie 免签名）→ 短视频基本信息    0.6s
L2  detail + a_bogus（ttwid + SM3） → 图集 / L1 兜底   1.0s
L3  play_addr.uri + /aweme/v1/play/?ratio= → 1080P    0.1s
```
L3 是本轮新增，解决 v2 只有 720P 的硬限制。

### B站（纯 HTTP，零ffmpeg）
`view` 拿 cid → `playurl?fnval=0&platform=html5` → `durl[0]` **单文件含音轨**
- `dash: false` → 不需要 ffmpeg 合并
- `need_proxy: false` → CDN 是标准 `cn-jsnt-ct-01-*.bilivideo.com`，白名单可枚举
- Referer **必须**设为视频页自身
- 代价：匿名上限 720P
