## 4. 取舍决策（★ 抄 / ◐ 改造 / ✗ 不抄）

### ★ 抄（直接丰富功能线）
1. **文案提取（链接通道）** —— 我们的 meta.description + tags 就是文案数据，只需加一个产出形态。轻抖四通道里先把「链接提文案」做出来，输入同一份，双按钮双产出
2. **批量解析** —— 工具箱验证了需求；我们「解析不限次」的定位天然支持批量，是差异化卖点
3. **榜单/热点入口** —— 解决「解析低频」的死穴；先做热门话题聚合（静态+缓存），不做实时爬取
4. **轻抖课堂式内容营销** —— 零算力成本的获客与留存，排版成合规页同级的静态页即可
5. **客服入口 + 最近记录** —— 合规与体验补齐

### ◐ 改造后抄
6. **双按钮设计**（去水印 + 提取文案并列）—— 改成我们的「保存素材 + 提取文案」双产出
7. **会员 + 订单中心** —— 支付接入时一起做，积分中心缓一步
8. **NEW/内测 标签** —— 用于新功能灰度披露
9. **合规轻量化** —— 竞品在输入框旁放一行小字；我们保留独立合规页（更稳），但在输入框旁加同款轻量提示

### ✗ 不抄（与定位/红线冲突）
10. **AI 生成全家桶**（写作/绘图/漫剧/数字人）—— v2 方案红线「零 AI 依赖」：
    ① 算力成本不可控（图生视频/数字人烧钱）
    ② 偏离「解析下载」定位，审核类目也会变
    ③ 全家桶 40+ 工具的维护成本远超小团队
11. **账号数据工具**（查权重/估值）—— 需要第三方数据源，且涉平台数据合规
12. **文件转换矩阵** —— 与主线无关，放弃（若未来做 P2 也只挑 PDF 转 Word 一两个）

## 5. 功能线扩展方案

### 5.0 ⭐ 全家桶工具的算力分级（2026-10-07 补充）

全家桶 40+ 工具逐个按算力消耗分类，**「不依赖 AI 算力」的比想象中多**：

**零算力（纯规则/纯逻辑，可直接抄）**
| 工具 | 实现方式 | 对我们 |
|---|---|---|
| 免费去水印 | 解析下载源头干净文件（**= 我们的主业**）| 已有，8 平台领先 |
| 免费文案提取（链接通道） | 解析拿 description/tags（**meta.py 已有数据**）| ⭐ P0 |
| 提词器 | 纯前端文本滚动，零后端 | P2（获客型小工具）|
| 视频加字幕 | ffmpeg 烧字幕，CPU | P2 |
| 视频格式转换 | ffmpeg，CPU | P2 |
| 文档格式转换 ×7 | 服务端 LibreOffice / 开源库，CPU | 暂缓（偏离主线）|
| 文本比较 | 纯算法 | 不做 |
| 文案库 | 存储类 | 已规划 |

**轻算力（CPU 转码，非 AI 模型，成本可控）**
- 视频压缩、格式转换类 —— ffmpeg 吃 CPU 和带宽，不烧钱但偏离主线

**重算力（AI 模型推理，绝不碰 —— v2 红线）**
- 文生图 / 图生视频 / 照片跳舞 / 视频唱歌 / 照片唱歌 / 数字人 / 混剪推文
- AI对话 / AI伪原创 / 文章续写 / AI证件照 / 图片橡皮擦 / 人声分离
- 校园必备 / 职场创意 / 社交媒体 三个分类的全部写作工具（LLM）
- AI漫剧（重度）

**⚠️ 需注意的半算力项**（按通道区分）：
| 工具 | 无算力通道 | 有算力通道 |
|---|---|---|
| 文案提取 | **链接解析**（拿现成文案）| 视频转文字（需 ASR）|
| 视频转字幕 | — | 需 ASR |
| 视频去字幕 | 裁剪/遮挡（损画质）| AI inpainting |

**商业模型洞察**：全家桶用「免费去水印 + 免费文案提取」（NEW 标引流）获客，
用 AI 生成变现。**没有 AI 变现能力的我们，替代变现位的就是会员体系** ——
所以零算力工具对我们是纯获客，成本近似零，可放心抄。

### 5.2 ⭐ 文件转换矩阵的专项分析（2026-10-07 用户追问）

**结论先行**：不依赖 AI 算力 ✅，但「不算力」≠「没成本」—— 它吃**服务器 CPU + 双向流量**，恰好打在我们两个最紧的约束上。

**按实现难度分三档**：

| 档 | 工具 | 引擎 | 真实成本 |
|---|---|---|---|
| 极轻 | PDF 合并 / 拆分 / 加水印 / 旋转 | pypdf（纯 CPU，毫秒级）| ≈0，可忽略 |
| 中等 | PDF 转图片、PPT 转图片 | pdftoppm / LibreOffice，秒级 | CPU 短时占用 |
| **重** | **Word/PPT/Excel ↔ PDF 互转**、PDF 转 Word | **LibreOffice headless** | ⚠️ 单次 2–5 秒 CPU + **内存峰值 300–500MB** |

**三条细化理由（替代原来的「偏离主线」一句话）**：

1. **服务器资源冲突**：验证机 2C2G。LibreOffice 转一个复杂 PPT 内存峰值 300–500MB ——
   并发 3 个转换就吃满 2G 内存，**解析服务（主业务）直接 OOM**。
   要做必须升配（2C4G 起步），为副线功能升配主服务器，顺序颠倒。
2. **双向流量成本**：解析是「只透传地址，流量走平台 CDN（¥0）」—— 这是成本方案的 A 级最优。
   文件转换是**上传 10MB → 服务器处理 → 下发 8MB**，双向都走我们的带宽。
   按 1000 次/天 ≈ 18GB/天 ≈ 540GB/月 —— **验证机月流量上限才 1TB**，文件转换一项就吃掉一半以上。
3. **用户画像不重叠**：我们的用户是自媒体创作者（素材场景），文件转换服务办公文员。
   获客价值存疑，却要付最贵的资源。

**若未来数据证明要做，方案对照**：
| 方案 | 内容 | 成本 | 建议 |
|---|---|---|---|
| A | 完全不做 | ¥0 | ✅ 维持 |
| B | 只做**极轻三件**（PDF 合并/拆分/加水印，pypdf 毫秒级） | ≈¥0 | P2 可选 |
| C | 全套 LibreOffice 互转 | 升配 2C4G + 流量费 | ❌ 除非 M3 后服务器升配 |
| D | 接第三方转换 API 转售 | 按次付费给服务商 | ❌ 毛利被剥两层 |

**一句话**：文件转换不是算力问题，是**资源排位问题** —— 2C2G 的每一兆内存都应该留给解析主业务。
