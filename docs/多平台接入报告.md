## 1. 核心发现：两个平台都需要浏览器

### 1.1 抖音：纯 HTTP 确认不可行

我按 `lzwme/m3u8-dl` 的思路测了「移动端分享页 → `_ROUTER_DATA` → `play_addr.uri` → `aweme/v1/play/`」：

```
[video] HTTP 200 32335 字节  _ROUTER_DATA=True  ✅ 解析成功
  ❌ 没有 item_list
```

进一步对比测试：

| 域名 | 字节 | `_ROUTER_DATA` | `item_list` | `play_addr` | 含标题 |
|---|---|---|---|---|---|
| `www.iesdouyin.com` | 32265 | 1 | **0** | **0** | ❌ |
| `m.iesdouyin.com` | — | 连接失败 | — | — | — |
| `iesdouyin.com` | — | 连接失败 | — | — | — |

⚠️ **页面连标题文字都没有** —— 与之前发现的 `video_layout: null` / `serverToken: ""` 一致。抖音对非浏览器请求不注入数据。

**结论：抖音必须用 Playwright，这个改不了。**

### 1.2 B站：同样需要浏览器

我先写了纯 HTTP 版本（正则抓 `__playinfo__`），结果：

```
[1080p] ❌ 未找到 __playinfo__（B站风控或页面结构变更）
```

改成浏览器后一次通过。

**结论：B站的 `__playinfo__` 只对真实浏览器注入，纯 HTTP 拿不到。**

## 3. 🔴 B站的三个硬限制（必须处理）

### 限制一：匿名会话只给 480P

`accept_quality` 声明支持 `1080P+`，但**实际只返回 480P**：

```
852x480  avc1  (H.264)
852x480  hev1  (H.265)
852x480  av01  (AV1)
640x360  avc1 / av01 / hev1
```

**解法**：配置 `CB_BILI_COOKIE` 提供登录 Cookie（已在 config 预留字段）。

### 限制二：CDN 域名带随机性 → 必然超白名单

实测 6 个域名，形态是随机的：

```
xy120x220x70x61xy.mcdn.bilivideo.cn:8082
xy116x196x140x43xy.mcdn.bilivideo.cn:8082
svx22w.edge.mountaintoys.cn:4483
b-baaai00e482fej1b365ionuahi8c.edge.mountaintoys.cn:4483
```

⚠️ `xy120x220x70x61xy` 这种是**每次请求随机生成的**（`xy` + 随机数字 + `xy`），**无法预先枚举**。加上 B站 MCDN 有数百个边缘节点，**必然超出微信 20 个白名单上限**。

**结论：B站必须走服务端中转**（已在响应中标记 `need_proxy: true`）。

### 限制三：音视频分离（dash）

视频和音频是**两条独立 URL**：

```
video: https://...137649199_da2-1-30032.m4s
audio: https://...137649199_da2-1-30216.m4s
```

**小程序端无法直接播放**（video 组件只认单文件），**必须服务端 ffmpeg 合并，或转成 m3u8**。

> ⚠️ 这意味着 B站要走 ffmpeg GPU/CPU 服务，是**新的成本项**。

## 5. 调研得到的关键情报（来自开源项目）

### 5.1 字段表（全部读自源码，非推测）

| 平台 | 无水印字段路径 | 获取方式 | 签名 | 浏览器 |
|---|---|---|---|---|
| 抖音 | `aweme_detail.video.bit_rate[].play_addr.url_list` | 纯HTTP | 需 a_bogus | 是（实测） |
| 抖音图文 | `aweme_detail.images[].url_list[2]` | 同上 | 同上 | 是（实测） |
| **B站** | `data.dash.video[].baseUrl` | 正则抓 `__playinfo__` | 不需要 | 是（实测） |
| 小红书 | `noteDetailMap[firstId].note.video.consumer.originVideoKey` | 正则抓 `__INITIAL_STATE__` | 不需要 | 是 |
| 快手 | `VisionVideoSetRepresentation` 的 `srcNoWatermark` | 正则抓 `__APOLLO_STATE__` | 不需要 | 是 |
| 好看视频（百度） | `curVideoMeta.clarityUrl[-1].url` | 正则抓 `__PRELOADED_STATE__` | 不需要 | 是 |
| 微博 | `Component_Play_Playinfo.urls` | POST `weibo.com/tv/api/component` | 需用户 Cookie | 是 |

⚠️ **一个值得验证的发现**：`wwwzhouhui/video-parser` 的抖音实现**优先取 `url_list[2]` 而非 `[0]`** —— 我实测发现第 3 个才是 jpeg（[0][1] 是 webp），**这个细节与我自己的发现吻合**。

### 5.2 `uvd` 项目（MIT 声明但无 LICENSE 文件）

**声称「纯 HTTP + A-Bogus，不依赖浏览器」** —— 如果能用，能省掉 500MB-1GB 的浏览器开销。

⚠️ 但子代理读完源码的结论是：**它没有解决 TLS 指纹问题**，只是用默认 httpx，差异可能在参数组合（匿名 ttwid + 24个公共参数 + `msToken=""` + 故意用老 UA `Chrome/90`）。

**建议：值得实测，但优先级低于已跑通的方案。** 且算法血缘含 GPL 3.0（JoeanAmier），商用需自行重写 SM3+RC4（国密标准和公开算法，重写不难）。

### 5.3 `VnaSeek`（**完全无许可证，不可商用**）

架构：前端 FFmpeg.wasm + 后端 StreamingResponse 逐字节转发。

⚠️ **「不落盘」省的是磁盘，不省带宽** —— 20MB 视频 = 20MB 入向 + 20MB 出向 = 40MB 流量。**对带宽成本是负优化。** 只值得借鉴 header 透传模式（只传 `range` / `if-range`）。

## 8. 成本影响修正

B站需要 ffmpeg 合并，**这是新增成本项**：

| 项 | 月成本 |
|---|---|
| 浏览器实例（抖音 1 + B站 1） | ¥200–400 |
| **ffmpeg 合并服务**（B站专用，2C4G 起步） | ¥100–200 |
| 带宽（抖音 ¥0 + B站需中转） | 视用量 |

⚠️ **B站的经济模型比抖音差**：多了 ffmpeg 成本 + 中转带宽 + 画质上限。建议**把 B站 做成次要平台**，主推抖音。
