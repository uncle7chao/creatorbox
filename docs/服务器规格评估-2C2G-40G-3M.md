# 服务器规格评估：2核2G / 40G / 3M 够不够用

> 2026-10-23 · 基于**实测数据**（不是估算）
> 结论：**纯解析服务完全够用，还有大量余量。有三个禁区。**

---

## 0. 直接回答

| 资源 | 买了 | 实际用 | 余量 | 判断 |
|---|---|---|---|---|
| 内存 | 2 GB | 约 500 MB | **1.5 GB** | ✅ 够 |
| 硬盘 | 40 GB | 约 12 GB | **28 GB** | ✅ 够 |
| 带宽 | 3 Mbps（**384 KB/s 速率**） | 峰值约 13 KB/s | **几乎空着** | ✅ 够 |

**但有三件事这台机器干不了**（见 §4）。

---

## ⚠️ 前置概念：带宽 ≠ 流量

这两个词经常被混用，但计费和判断逻辑完全不同：

| | 带宽（Bandwidth） | 流量（Traffic） |
|---|---|---|
| 是什么 | 水管**粗细**（Mbps，速率上限） | 流过的**水量**（GB，总量） |
| 会不会"用超" | **不累积** → 没有"用超"这回事 | 会，超了要加钱或限速 |
| 账单逻辑 | 按月固定（买多粗就付多少） | 按量（用多少付多少） |
| 判断标准 | **瞬时是否打满** | 总量是否超包 |

⚠️ **本文档所有带宽数字都是"速率"，不是"总量"。**
3M 的意思是「每秒最多传 384 KB」，不是你一个月有 384KB 的配额。
**今天传 1 GB 还是 100 GB，只要每秒不超 384 KB，账单完全一样。**

"按固定带宽计费"= 买速率 + **不限总量**。所以不存在"这个月流量用超了要加钱"。

## 1. 内存：实测服务只占 60 MB

### 实测数据

| 项目 | 数值 | 测量方式 |
|---|---|---|
| FastAPI + uvicorn + 全部模块 | **60 MB** | `Get-Process python`（服务跑起来后） |
| 全部 python 进程合计 | 101 MB | `tasklist` 汇总 |
| 5 并发解析 | 2.80 秒，5/5 成功 | 并发压测 |
| 压测前后内存变化 | **0 MB** | 同上 |

### 内存预算（Linux 生产环境）

| 项 | 估算 |
|---|---|
| Ubuntu 22.04 系统本身 | 300 MB |
| 解析服务 1 worker | 60 MB |
| （2 核建议开 2 worker） | 120 MB |
| SQLite + 文件页缓存 | 150 MB |
| **合计基线** | **约 500 MB** |
| **2G 剩余** | **约 1.5 GB** |

**结论**：余量充足。即使日活涨到几千，内存也不是瓶颈（瓶颈在带宽，见 §3）。

## 2. 硬盘：需要约 12 GB

| 项 | 占用 |
|---|---|
| Ubuntu 22.04（最小安装 + 常用工具） | 7.8 GB |
| Python 3.10 + pip 依赖 | 0.6 GB |
| 项目代码（server + miniapp + app_flutter） | 0.01 GB |
| SQLite 数据库（10 万用户估） | 0.05 GB |
| 日志（**不轮转**，3 个月） | 2.9 GB |
| Playwright Chromium（如需浏览器通道） | 0.4 GB |
| **合计** | **约 11.8 GB** |
| **40G 剩余** | **约 28 GB** |

### ⚠️ 唯一会吃硬盘的是日志

- **不轮转**：3 个月约 3 GB（每天几十次解析 × 请求日志）
- **日活几千时**：可能 1 GB/月以上
- **必须配 logrotate**，保留 7~14 天

```bash
# /etc/logrotate.d/creatorbox
/var/log/creatorbox/*.log {
    daily
    rotate 14
    compress
    missingok
    notifempty
    copytruncate
}
```

## 3. 带宽：3M 完全够

### ⭐ 两个关键前提

**前提一：带宽只管出网（下行不计费、不受限）**

阿里云官方原文：

> **阿里云仅对出方向流量计费，入方向不计费。**
> 带宽值**为出网带宽上限**，实际的出网带宽不会高于指定的带宽值。

| 动作 | 方向 | 受 3M 限制吗 |
|---|---|---|
| 服务器抓平台页面（800 KB） | **入网** | ❌ 不受限、不计费 |
| 服务器返回 JSON 给客户端（8 KB） | **出网** | ✅ 受限 |

**前提二：3M 是速率，不是总量（见 §0 的概念表）**

3M = 每秒最多传 384 KB。**它不累积**，所以不存在"用超"——
判断标准是「瞬时会不会打满」，不是「总量用了多少」。

### 解析场景的瞬时速率占用

```
高峰 1 小时 600 次解析 → 平均 0.17 次/秒
每次出网 8 KB → 平均瞬时 1.33 KB/s
占 3M 上限（384 KB/s）的 0.35%

即使瞬时峰值是平均的 10 倍 → 13.3 KB/s = 3.5%
```

⚠️ 注意这里的 0.35% 是「**瞬时速率**占带宽上限的比例」，
**不是**「这个月流量用掉了 0.35%」。带宽没有"用掉"的概念。

### 3M 的真实天花板（这才是该看的数）

```
打满 3M = 384 KB/s ÷ 8 KB/次 = 48 次/秒 = 2,880 次/分钟
```

**意思是：每秒最多 48 个解析请求同时返回。**
日活 3000 的峰值（0.17 次/秒）距离这个天花板还差 **280 倍**。

**结论：3M 对纯解析绰绰有余，永远不会成为瓶颈。**


### ⚠️ 唯一要留意的一句话

**视频不经过我们服务器** —— 客户端 `wx.downloadFile` 直连平台 CDN，
25MB 也好 100MB 也好，我们出网 0 字节。所以带宽只需要服务解析。

（`need_proxy` 那个标记只在「直连失败」时兜底用，占比极低，
不用当成带宽规划的依据 —— 之前我在文档里反复拿它当反例，是多余的。）

## 4. 两条要守的线

### ① 浏览器通道（小红书）—— 2G 跑不动

- 服务端有 `signed_platforms.py`（Playwright 方案），用于小红书等需要 JS 渲染的平台
- **Chromium 每个实例 400~500 MB**（主进程 + 渲染进程 + GPU 进程）
- 2G 内存只能跑 1~2 个实例，并发一多就 OOM
- 硬盘还要 +400 MB

**结论**：2G 机器**不要开浏览器通道**。要么升到 4G，要么小红书不做
（或让用户自己在浏览器里复制直链）。

### ② 日志必须轮转

见 §2：3 个月能吃 3 GB，长期跑会满。

**结论**：部署时必须配 logrotate（配置见 §2）。

## 5. 与 ECS 计费方式的关系

| 计费方式 | 流量 | 本规格价格参考 |
|---|---|---|
| **按固定带宽 3M** | **不限流量** | 阿里云 ECS 2C2G/3M 活动价约 ¥99/年 |
| 按使用流量 | 3M 只是峰值上限，按 GB 计费 | 用量小可能更便宜，但不可控 |

⭐ **推荐按固定带宽**：3M 对解析服务完全够，且不限流量，不用盯账单。

### 购买时必须确认的三点

1. **活动价是否限新用户 / 首年**？续费可能恢复标准价（差 8~10 倍），要让销售书面确认
2. **包年 ≥3 个月才能备案**（ECS 官方规则）
3. 3M 够解析（视频本来就直连 CDN，不占我们带宽）；但**别指望它跑浏览器通道**

## 6. 什么情况下需要升级

| 触发条件 | 升级到 | 理由 |
|---|---|---|
| 要开小红书浏览器通道 | **内存 4G** | Chromium 每个 400~500MB |
| 日活 > 8000（按轻量流量包算） | 换 ECS 固定带宽 / 加大流量包 | 避免限速 |
| 日志超 10 GB | 先查轮转配置是否生效 | 99% 是没配 logrotate |

---

## 7. 一句话总结

**2核2G / 40G / 3M 跑纯解析服务，余量很大。**

- 内存：用 500MB / 2GB，剩 1.5GB
- 硬盘：用 12GB / 40GB，剩 28GB
- 带宽：**瞬时 1.3 KB/s，上限 384 KB/s**（速率，不是总量 —— 不存在"用超"）

视频流量完全不经过我们服务器（客户端直连 CDN），所以带宽只需承载解析的 JSON。

**只要守住两条线：不开浏览器通道（2G 跑不动）、日志必须轮转。**
