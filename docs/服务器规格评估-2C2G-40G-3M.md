# 服务器规格评估：2核2G / 40G / 3M 够不够用

> 2026-10-23 · 基于**实测数据**（不是估算）
> 结论：**纯解析服务完全够用，还有大量余量。有三个禁区。**

---

## 0. 直接回答

| 资源 | 买了 | 实际用 | 余量 | 判断 |
|---|---|---|---|---|
| 内存 | 2 GB | 约 500 MB | **1.5 GB** | ✅ 够 |
| 硬盘 | 40 GB | 约 12 GB | **28 GB** | ✅ 够 |
| 带宽 | 3 Mbps | 0.35%（解析场景） | **99.6%** | ✅ 够 |

**但有三件事这台机器干不了**（见 §4）。

---

## 1. 内存：实测服务只占 60 MB

### 实测数据

| 项目 | 数值 | 测量方式 |
|---|---|---|
| FastAPI + uvicorn + 全部模块 | **60 MB** | `Get-Process python`（服务跑起来后） |
| 全部 python 进程合计 | 101 MB | `tasklist` 汇总 |
| 5 并发解析 | 2.80 秒，5/5 成功 | 并发压测 |
| 压测前后内存变化 | **0 MB** | 同上 |

### 内存预算（Linux 生产环境）

| 项 | 估算 |
|---|---|
| Ubuntu 22.04 系统本身 | 300 MB |
| 解析服务 1 worker | 60 MB |
| （2 核建议开 2 worker） | 120 MB |
| SQLite + 文件页缓存 | 150 MB |
| **合计基线** | **约 500 MB** |
| **2G 剩余** | **约 1.5 GB** |

**结论**：余量充足。即使日活涨到几千，内存也不是瓶颈（瓶颈在带宽，见 §3）。

---

## 2. 硬盘：需要约 12 GB

| 项 | 占用 |
|---|---|
| Ubuntu 22.04（最小安装 + 常用工具） | 7.8 GB |
| Python 3.10 + pip 依赖 | 0.6 GB |
| 项目代码（server + miniapp + app_flutter） | 0.01 GB |
| SQLite 数据库（10 万用户估） | 0.05 GB |
| 日志（**不轮转**，3 个月） | 2.9 GB |
| Playwright Chromium（如需浏览器通道） | 0.4 GB |
| **合计** | **约 11.8 GB** |
| **40G 剩余** | **约 28 GB** |

### ⚠️ 唯一会吃硬盘的是日志

- **不轮转**：3 个月约 3 GB（每天几十次解析 × 请求日志）
- **日活几千时**：可能 1 GB/月以上
- **必须配 logrotate**，保留 7~14 天

```bash
# /etc/logrotate.d/creatorbox
/var/log/creatorbox/*.log {
    daily
    rotate 14
    compress
    missingok
    notifempty
    copytruncate
}
```

## 3. 带宽：3M 完全够（关键理解：带宽只管出网）

### ⭐ 这是最容易误解的一点

阿里云官方原文：

> **阿里云仅对出方向流量计费，入方向不计费。**
> 带宽值**为出网带宽上限**，实际的出网带宽不会高于指定的带宽值。

也就是说：

| 动作 | 方向 | 受 3M 限制吗 |
|---|---|---|
| 服务器抓平台页面（800 KB） | **入网** | ❌ 不受限、不计费 |
| 服务器返回 JSON 给客户端（8 KB） | **出网** | ✅ 受限 |
| 视频中转（25 MB） | **出网** | ✅ 受限（这是禁区） |

### 解析场景：出网只有 8 KB/次

```
3 Mbps = 384 KB/s
384 KB/s ÷ 8 KB/次 = 48 次/秒 = 172,800 次/小时

日活 3000（6000 次/天，峰值按 10%/小时 = 600 次）
→ 用掉 600 / 172,800 = 0.35%
```

**结论：3M 对纯解析绰绰有余，不是瓶颈。**

### 反面：视频中转会立刻卡死

```
3 Mbps = 0.375 MB/s
25 MB 视频 ÷ 0.375 = 67 秒/个
→ 3600 / 67 = 54 个/小时

日活 1000、10% 下载 = 100 个/天 → 需要 1.9 小时才传完
```

⚠️ 如果下载集中在晚上 2 小时高峰，用户会明显排队。

## 4. 三个禁区（这台机器干不了的事）

### ① 浏览器通道（小红书）

- 服务端有 `signed_platforms.py`（Playwright 方案），用于小红书等需要 JS 渲染的平台
- **Chromium 每个实例 400~500 MB**（主进程 + 渲染进程 + GPU 进程）
- 2G 内存只能跑 1~2 个实例，并发一多就 OOM
- 硬盘还要 +400 MB

**结论**：2G 机器**不要开浏览器通道**。要么升级到 4G，要么小红书不做（或用户自己在浏览器里复制直链）。

### ② 视频中转

见 §3：3M 出网只能 54 个/小时。

**结论**：必须靠客户端直连平台 CDN。`need_proxy` 只能作为**直连失败时的兜底**，不能全量中转。

### ③ 日志不轮转

见 §2：3 个月能吃 3 GB，长期跑会满。

**结论**：部署时必须配 logrotate。

## 5. 与 ECS 计费方式的关系

| 计费方式 | 流量 | 本规格价格参考 |
|---|---|---|
| **按固定带宽 3M** | **不限流量** | 阿里云 ECS 2C2G/3M 活动价约 ¥99/年 |
| 按使用流量 | 3M 只是峰值上限，按 GB 计费 | 用量小可能更便宜，但不可控 |

⭐ **推荐按固定带宽**：3M 对解析服务完全够，且不限流量，不用盯账单。

### 购买时必须确认的三点

1. **活动价是否限新用户 / 首年**？续费可能恢复标准价（差 8~10 倍），要让销售书面确认
2. **包年 ≥3 个月才能备案**（ECS 官方规则）
3. 3M 够解析，但**别指望做视频中转或浏览器通道**

## 6. 什么情况下需要升级

| 触发条件 | 升级到 | 理由 |
|---|---|---|
| 要开小红书浏览器通道 | **内存 4G** | Chromium 每个 400~500MB |
| 要做视频中转 | **带宽 50M+** | 3M 只能 54 个/小时，且 10M 以上带宽单价跳档（~70元/Mbps/月） |
| 日活 > 8000（按轻量流量包算） | 换 ECS 固定带宽 / 加大流量包 | 避免限速 |
| 日志超 10 GB | 先查轮转配置是否生效 | 99% 是没配 logrotate |

---

## 7. 一句话总结

**2核2G / 40G / 3M 跑纯解析服务，余量很大（内存剩 1.5G、硬盘剩 28G、带宽用 0.35%）。**

**但要守住三条线：不开浏览器通道、不做视频中转、日志必须轮转。**
