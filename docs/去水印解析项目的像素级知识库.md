## 二、parse-video-py：像素级功能拆解（25 平台解析器集合）

### 2.1 四种使用形态（一个库四种卖法）
| 形态 | 入口 | 面向 |
|---|---|---|
| Python 库 | `from parse_video_py import parse_video_share_url` | 开发者集成 |
| CLI | `parse-video-py parse <urls> --format json --file urls.txt` | 脚本党 |
| Web 服务 | `parse-video-py serve --host --port`（FastAPI + uvicorn） | 自部署 |
| **MCP 服务** | `FastApiMCP(app)` + `mcp.mount_http()` | **AI Agent 调用**（2025 年的新玩法，我们能直接抄） |

### 2.2 API 面（3 个端点）
```
GET /                        Demo 页（Jinja2 模板）
GET /video/share/url/parse?url=   分享链接解析（自动 extract_url 提取）
GET /video/id/parse?source=&video_id=  按 ID 精确解析
```
- 全端点挂 **Basic Auth 依赖**（环境变量 `PARSE_VIDEO_USERNAME/PASSWORD`，`secrets.compare_digest` 防时序攻击；未配置=不鉴权）
- 统一响应 `{code: 200/400/500, msg, data}`；**错误不抛 500，永远 200 + code 字段**（客户端好处理）
- `extract_url()` 从分享文案里提取链接（和我们的 URL_RE 同一个需求）

### 2.3 数据模型（VideoInfo —— 比我们想的少得多）
```
VideoInfo { video_url, cover_url, title, music_url, images: [ImgInfo], author: VideoAuthor }
ImgInfo { url, live_photo_video_url }    VideoAuthor { name, avatar }
```
⭐ **只有 6 个顶层字段** —— 竞品不卷元信息，我们 meta 规范化（播放量/时长等）反而是差异化超配。`music_url`（背景音乐提取）是我们没有的字段，用户实际会用来做二创取 BGM。

### 2.4 工程细节
- UA 用 `fake_useragent`（iOS 随机池），不是固定 UA
- 25 个解析器一个文件一个平台，`video_source_info_mapping` 域名路由表分发
- 抖音唯一有子目录（多级降级）；其余平台全是一把梭

### 2.5 与 2026-10-05 版报告的差异（本轮新发现）
- 新增 `huya.py`（虎牙直播）、`quanmin.py`、`quanminkge.py` —— **直播流平台也在被收编**
- 加了 MCP 层 —— 解析能力被包装成 AI Agent 工具是明确趋势

## 三、parse-video (Go)：五层中间件 + 生产级服务范本

### 3.1 中间件栈（顺序即架构，直接照抄到我们服务）
```
Recovery → CORS(CORS_ORIGINS 可配) → 请求日志 → IP 速率限制(RATE_LIMIT_RPM 默认 60) → Basic Auth(豁免 /health /platforms /)
```
⭐ 比我们现在的中间件多了「**豁免路径表**」——健康检查和静态资源不吃鉴权/限流额度，避免探针把自己打死。

### 3.2 路由全表
```
GET  /                              Web UI（Go template 内嵌 FS）
GET  /api/v1/health                 健康检查
GET  /api/v1/platforms              平台枚举（客户端动态发现，不硬编码）
GET  /api/v1/parse?url=             分享链接解析
GET  /api/v1/parse/:source/:video_id  按 ID 解析
GET  /video/share/url/parse         旧路由兼容
GET  /video/id/parse                旧路由兼容
```
⭐ **新旧路由并存**——改 API 路径时保留旧路由，客户端零迁移。我们改接口时该学。

### 3.3 CLI（比 Py 版多一个下载器）
```
parse <urls> --format text|json --file urls.txt(每行一条,-=stdin) --download -d --output-dir -o
```
⭐ `--download` 把「解析结果」变成「落盘文件」——CLI 党的真实需求是拿到文件不是 JSON。

### 3.4 抖音真签名（a_bogus 生产级实现）
- 35 个固定参数（版本号 29.1.0 / 1920×1080 / Chrome 130 全套设备指纹）+ cookie 从 `PARSE_VIDEO_DOUYIN_COOKIE` 读，未设置直接报错（fail-fast）
- 算法：`SM3(SM3(params))` 双重哈希 + RC4（密钥单字节 `"y"`）+ 自定义 Base64 表 `Dkdpgh2ZmsQB80/...`
- ⚠️ **降级链 4 级**：canonical 判断图文 → slidesinfo（假签名随机串）→ SSR 正则 → detail 真签名。**假签名能通是因为 slidesinfo 不校验**——这是「伪装成本」最低的通道，我们 L1 通道的原理依据。

## 四、m3u8-dl：下载管理全家桶（功能最完整的 WebUI）

### 4.1 CLI（17 个参数，谈判筹码级别的完备）
```
m3u8dl <m3u8Urls...>
  --silent --debug -f 文件名 -n 线程数 -F 强制覆盖 --no-progress
  -p 播放 -C 缓存目录 -S 保存目录 --no-del-cache --no-convert
  --ffmpeg-path -H 自定义请求头 -T 类型 -I 忽略时间段 --lang
server -P 端口      ← 同一个二进制起 WebUI
批量：支持「文件路径」当参数（文件内每行一条 m3u8，自动编号）
```

### 4.2 WebUI API 全表（13 端点 = 一个完整下载管理器）
```
GET  /healthcheck
GET/POST /api/config          运行时配置读写（线程数/保存目录可热改）
GET  /api/tasks               任务列表（含进度/状态/速度）
GET  /api/queue/status        队列水位
POST /api/queue/clear         清队列
POST /api/download            提交下载（异步任务）
POST /api/pause /api/resume   暂停/恢复（分片级断点）
POST /api/delete /api/rename  删除/重命名（文件管理器语义）
GET  /localplay/{path}        本地文件流式播放（下载完直接在线看）
POST /api/getM3u8Urls         从网页提取 m3u8 地址（分析器）
```
⭐ 三个我们没想到的功能：**pause/resume 到分片级**、**localplay 在线播放刚下载的文件**、**rename 文件管理语义**。这就是「下载器产品化」的样子。

### 4.3 下载内核参数（2C 服务器调优参考值）
| 项 | 值 | 出处 |
|---|---|---|
| 分片并发 | min(CPU×2, **8**) | format-options.ts:107 |
| 任务并发 | 默认 **3** | m3u8-download.ts:25 |
| 分片重试 | 3 次 | m3u8-download.ts:283 |
| AES-128 | `createDecipheriv('aes-128-cbc')` | crypto.ts:44 |
| **SAMPLE-AES** | ❌ 不支持（样本级加密≠整段解密） | crypto.ts:13-15 |
| BYTERANGE | ✅ offset 继承 | utils.ts:25 |

### 4.4 ffmpeg 合并策略模式（三条命令）
- fMP4：initSegment+分片二进制拼 → `-c copy -movflags +faststart`
- TS：ffconcat 清单 → `-async 1 -f concat -safe 0 -c copy -bsf:a aac_adtstoasc`
- **binaryMerger 兜底**：无 ffmpeg 环境纯二进制拼（能看不能 seek）
- `registerMerger()` 注册新容器 —— 策略模式，可扩展

⚠️ **安全弱点**：WebUI token = md5 前 8 位（32 位熵、无过期），公网部署必须重写 —— 我们 `check_auth` 的 API Key 方案比它强。

## 五、video-parser：Gradio + AI 抽帧（HuggingFace 路线）

### 5.1 双服务架构
- `app.py` = **Gradio Blocks 应用**（HuggingFace Spaces 一键部署路线）：`gr.Progress()` 进度条、示例链接点击填充、在线播放 tab
- `api.py` = FastAPI 正经 API：`/health`、`/api/parse`、`/api/download`
- **一个引擎两种皮**：核心 downloader 复用，Gradio 给白嫖用户，FastAPI 给 API 用户

### 5.2 8 个 downloader 手段速查
| 平台 | 手段 | 关键差异 |
|---|---|---|
| 抖音 | **py_mini_racer 跑 JS 版 a_bogus** | V8 引擎跑原版 JS，比纯 Python 重写更不易碎 |
| 小红书 | SSR `__INITIAL_STATE__` → `originVideoKey` 拼 CDN | 不签名 |
| 快手 | SSR `__APOLLO_STATE__` | ⚠️ 硬编码 cookie 含 userId，随时挂 |
| 好看视频 | `clarityUrl[-1]` | 需 unquote + `\/`→`/` |
| B站 | dash 双流（video+audio baseUrl） | 需要 ffmpeg 合并（比我们 durl 方案多一步） |

### 5.3 Qwen3-VL 抽帧（AI 理解视频内容）
```
ffmpeg 抽帧（默认 6 帧）→ base64 → ModelScope API（OpenAI 兼容, api-inference.modelscope.cn）
```
- 无 GPU、免部署，ModelScope 免费额度够玩但商用要钱
- **对我们的启示**：解析出的视频可以加「AI 看视频写文案」——但个人主体小程序内嵌生成式 AI 有算法备案问题，先不做（见第十一节）

### 5.4 Docker 极简主义
`python:3.11-slim` + ffmpeg，**无浏览器无模型权重** → 镜像小、内存低。与我们纯 HTTP 路线同哲学。

## 六、uvd：AI 总结层（最值得研究的产品化样本）

### 6.1 API 全表（6 组端点，含异步任务模式）
```
POST /api/info                   解析（含格式枚举 formats）
GET  /api/proxy-thumbnail/{encoded_url}   封面防盗链代理 ⭐
POST /api/download               异步下载任务
GET  /api/progress/{task_id}     轮询进度（_download_hook 回调驱动）
GET  /api/file/{task_id}         取成品文件
POST /api/ai/summarize           AI 总结任务（字幕→LLM）
GET  /api/ai/progress/{task_id}  AI 任务进度
GET  /api/ai/result/{task_id}    AI 结果
```
⭐ **三个产品化绝招**：
1. **proxy-thumbnail**：抖音封面带防盗链签名，服务端中转一次变永久可显示 —— 我们小程序里封面偶发裂图就是这个原因
2. **异步任务 + 轮询**：下载/AI 全部 task_id 化，前端不阻塞
3. **AI 分层降级**：`source: "subtitle" | "description" | "none"` —— 有字幕用字幕，没字幕用 description 兜底，都没有返回 none（诚实降级）

### 6.2 AI 管线细节（能抄的设计，不能抄的合规）
```
yt-dlp 拿 subtitles/automatic_captions → 拼文本 → LLM（AI_API_KEY 环境变量）
→ 产物：智能总结 + 章节大纲（前端两个 tab）
```
- 前端 `ai-summary.js`：startAISummary → pollAIProgress → fetchResult 三段式
- **个人主体小程序做这个要企业资质+算法备案** —— 技术照抄没问题，上不上看资质

### 6.3 抖音自研细节（与 Go 版互为印证）
- Cookie 只有 ttwid（`ttwid.bytedance.com/ttwid/union/register` 自助注册，缓存 24h）—— **不需要完整登录 Cookie**
- msToken 传空串；UA 固定 Chrome/90
- ⚠️ 图集未实现（/note/ 硬改 /video/）—— 图集是真门槛，我们已解决是优势

## 七、VnaSeek：流式转发路线 + 仓库进化警示

### 7.1 路由（backend.py，行号已变——上游在活跃更新）
```
GET  /api/health
POST /api/parse            yt-dlp 解析（含格式枚举）
POST /api/download-url     生成下载地址
GET  /api/stream/{token}   流式转发（StreamingResponse 逐字节搬运）
GET  /ffmpeg/class-worker.js   ffmpeg.wasm worker 静态下发
```
- **「不落盘」真相 = 双倍带宽**：0 处 RedirectResponse，`proxyUrl || directUrl` 默认走代理。2C 服务器转发 1080P 视频会把带宽打爆。**我们 302 重定向方案是对的。**
- 前端 **FFmpeg.wasm 合并**（B站 dash 音视频双流）：`-c copy` 纯流拷贝 + faststart，ffmpeg 全从 jsdelivr CDN 加载 —— 浏览器端合并是「服务器零成本」的极端方案，但移动端内存炸

### 7.2 前端分轨下载（用户价值点，直接可抄）
```
videoFormatSelect / audioFormatSelect   视频、音频分开选清晰度
downloadButton        下载视频
downloadAudioButton   只下音频（提取 BGM）
downloadCoverButton   只下封面
downloadDescriptionButton   只下文案
downloadSubtitleButton      只下字幕
```
⭐ **五个下载按钮 = 五种素材** —— 我们的「文案提取」是其中一种，音频/封面独立下载可以加进结果页。

### 7.3 ⚠️ 仓库进化警示（本轮重要发现）
VnaSeek 已不是纯解析服务——clone 下来是 **monorepo**：`beat_analyzer/`（视频解析服务本体）+ `chordinor_project/`（和弦工具）+ `desktop/`（Electron 壳）。**单人开发者也在往工具矩阵长**，且上游行号已与 10-05 版报告对不上。结论：研究竞品要盯仓库 evolution，快照会过期。

## 八、Yeguo-IDM：桌面下载管理器的功能清单（AGPL，只看思路）

### 8.1 PyQt5 桌面全功能面（12 个 UI 模块 + 14 个 core 模块）
```
UI：主窗口 / 历史对话框 / 预览对话框(下载前看) / 字幕对话框 / 设置 / 反馈 / 更新 / 帮助 / 视频播放器 / 滚动条美化
core：queue_manager(优先级队列) / history / ffmpeg_integrator+manager(自动找ffmpeg)
      netease_music_manager(网易云歌单!) / subtitle_manager(字幕) / preview_manager
      sound_manager(完成提示音) / i18n(中英) / update_manager(自动更新) / log_manager
workers：download_worker / parse_worker / netease_music_worker（线程池三件套）
```
⭐ 值得抄的 5 个产品细节：
1. **下载前预览**（preview_manager）——先看再下，减少废下载
2. **完成提示音**（sound_manager）——桌面软件的仪式感
3. **自动更新**（update_manager）——桌面分发必备
4. **网易云歌单批量下载**（get_song_info/get_playlist_songs/get_formats 三段式，含随机 UA+随机 IP）
5. **i18n 框架**从第一天就有（中文用户出海两不误）

### 8.2 下载历史 schema（直接可用）
```sql
download_history(url, title, filename, format_id, resolution, file_size,
                 download_path, download_time, duration, thumbnail_url,
                 platform, status, created_at) + 4 个索引
```
⚠️ 坑：`db_path=":memory:"` 纯内存，重启全丢 —— 抄 schema 不抄这个。

### 11.2 新收获（对知识库的增量修正）

1. **a_bogus 不只签 aweme/detail 接口** —— 滑动验证码的 verify 请求（`https://verify.zijieapi.com/...`）本身就带 `a_bogus` 参数。签名链在风控闸阶段就开始工作，覆盖面比我们此前记录的更宽。
2. **verify 请求参数全量枚举**（可做风控探测的参数模板）：`aid, lang, bd_version, subtype, detail, server_sdk_env(idc=lq,region=CN,server_type=whale), mode=slide, fp=verify_mv3val06_*, h5_check_version=3.5.2, os_name=windows, platform=pc, os_type=2, h5_sdk_version=3.5.81, webdriver, tmp, a_bogus`。
3. **msToken 分发机制实锤**：verify.zijieapi.com 的响应头带 **`x-ms-token`** —— 通过风控验证后 msToken 由响应头下发（此前知识库未记录该分发通道）。
4. **无头检测上报**：无头 CDP 访问时 verify 请求里明明白白带 `webdriver=true` —— 平台在验证请求里主动回传 webdriver 标志，P1b 真机验证必须走带指纹的真实浏览器上下文（有头 + 正常 UA），纯无头必被标记。
5. **acrawler/webmssdk 在闸前不加载**：挑战壳页只加载验证栈 7 个脚本，主签名包（byted_acrawler）是运行时构造加载器、且在通过验证后才进 —— 想抓最新 a_bogus 算法 bundle 必须用**带 Cookie/登录态**的浏览器上下文，裸无头访问永远抓不到。
6. **bdms.js 1.0.1.18 的混淆形态**：webpack 打包 + 自研 VM 字节码派发器（形如 `V(129, void 0, arguments, {get 0(){...}})`）+ 字符串全加密（全文 0 处明文 X-Bogus/msToken，只有 URL polyfill 等框架噪音）+ slardar 上报器（`https://mon.zijieapi.com/monitor_browser/collect/batch/?biz_id=web_bdms_cn`，release b-1.0.1.18）。**结论：纯静态逆向签名算法不可行，正确策略仍是「整包投喂 JS 运行时执行」**（与 dtk/Evil0ctal 路线一致，该路线未被证伪）。
7. **collect-base.js 暴露设备指纹注册端点**：`/webid`、`/tobid`、`/profile/list`、`/v1/list_test` —— tobid 是字节系跨应用设备 ID 概念，与 ttwid 平行，知识库名词表补录。
8. **验证码入口配置端点**：`/vc/setting`（sec_sdk_build 3.5.2），`s_v_web_id` Cookie 名在此出现。

### 11.3 可复用的逆向流水线（下次滚版时直接跑）

```
capture_browser_scenario(chromium, start_url=平台首页, 6s settle, capture network response_body)
  → export_web_scripts(带 SHA-256 manifest)
  → analyze_javascript_application(目录形态, record-and-continue)
  → 与 11.1 的版本指纹表 diff SHA-256 → 判断平台是否滚版
  → 版本变了 → 用带登录态浏览器重抓主签名 bundle → 重跑交叉验证
```

**本轮未达成的**：acrawler 主签名包未捕获（被闸拦截），故 dtk Python 移植与线上算法的**同步性结论暂为「无反向证据」而非「已验证一致」**；待用户提供带 Cookie 的浏览器上下文后补一轮。风险敞口不变：Evil0ctal 移植基于 2026-09 bundle，平台滚版即失效，P1b③ 的线上验证仍是必要防线。
